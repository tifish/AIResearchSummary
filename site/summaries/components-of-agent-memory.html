智能体记忆的组成部分

The components of agent memory

一句话总括：文章通过数据库问答、Pokémon 和文档任务的评估，说明智能体如何把经历变成可验证、可检索、可维护的记忆，并展示离线整理机制 dreaming 在其中的作用。

53% → 61%同一评估中，仅搜索的得分为 53%；搜索配合充分构建的 wiki 达到 61%。

记忆的收益，取决于能否形成验证闭环

在 CL-Bench 1.0 数据库任务中，Claude 每答完一题都会收到正确答案。下一题从新会话开始，但可以读取此前保存的记忆。较强模型不仅记录错误，还会验证原因，把结果写成有依据的规则。

记忆工具本身不会自动带来学习。模型还需要判断什么值得保存，并验证保存下来的规则。

更少的记忆，也能支持更远的进展

在约 10,000 步的 Pokémon Red 运行中，Sonnet 3.7 写了 413 个文件、225 个文件夹，获得 1 枚徽章。Fable 5 在 2 个文件夹中写了 9 个文件，另加一个顶层 global.md，获得 4 枚徽章。

Fable 5 更侧重策略、计划和已经检验的规则。屏幕上随时可见的状态不必重复存储。记忆的价值在于保留无法直接重新观察到的信息。

错误笔记会把后续行动带偏

Claude 曾把 PokéCenter 的方位记反，因而反复走错路。保留错误笔记的运行跌回原路线 3 次，最终没有到达 Cerulean City。

dreaming 对照会话记录纠正笔记后，Claude 返回洞穴并到达目标城市。跨会话保留信息，也意味着跨会话传播错误的风险。

dreaming 把记忆维护分成多个层次

  1. 回查记录
    对照原始会话记录，检验并纠正笔记。
  2. 建立表示
    构建互相链接的 wiki 页面，帮助定位知识。
  3. 维护顶层索引
    将少量重要信息放入每次会话自动加载的上下文。
  4. 跨会话补漏
    修复错误链接，增加缺失页面，发现共同模式。

Claude Code 的 auto memory 只加载 MEMORY.md 的前 200 行或 25 KB。顶层记忆因此需要保持精简，并通过链接指向详细内容。

这套分层方式让信息更容易被找到，但维护本身仍要消耗计算资源。

wiki 更适合综合信息，不一定适合简单检索

Stainless 评估使用约 35 万份文件、4.2 亿 token，并设置了 25 道问题。dreaming 逐步丰富 wiki 后，搜索与 wiki 结合的效果最好，每题还节省了约 20,000 token。

是否值得构建 wiki，取决于任务需要多少信息整合，而不只是文档数量有多大。

记忆质量也受协作方式影响

合同任务最初让多个智能体同时写入共享表格。它们覆盖了彼此的内容，最终只保留 41/57 项事实，即 72%。

问题不只是记忆容量不足。写入冲突和过度概括，也会丢失关键事实。

围绕目标调整结构，能修复具体失败

改进后的指令要求每份合同由一个智能体负责，单独建页，并逐字引用条款。全部 57/57 项事实得以保留，生成的简报能够满足 100% 的评分标准。

另一次 dreaming 还修复了 9 条指向缺失页面的链接，并新增 3 个页面。维护应针对任务中真正重要的信息和已发现的缺口。

最值得带走的洞见

  • 记忆是一种对未来需求的预测。保存经过验证的规则，比无差别记录经历更有价值。
  • 会话内记录与离线整理各有代价。前者及时但分散任务注意力，后者需要计算资源，产出也未必能立即使用。
  • 检索与 wiki 可以互补。需要跨文档综合时，结构化知识更有用；简单文本查找未必受益。
  • 记忆系统需要纠错机制。原始记录可用于核验，顶层索引应保持精简，过时信息和错误表示需要持续维护。

Søren Kierkegaard 写道，人生只能回头看才能理解，却必须向前走。我们在为 AI 智能体设计记忆时，也遇到了类似的两难。

人类在日常生活中会不断编码记忆。海马体在其中发挥着核心作用。它即时捕捉经历，让记忆快速形成，并能立即被调用。不过，只有部分经历会被巩固为长期知识。

许多这样的巩固过程，似乎发生在大脑“离线”时。在睡眠和安静休息期间，海马体会重放近期经历。研究者认为，这个过程会逐渐提炼这些经历，并将它们整合进新皮层。我们通常所说的知识，大多就储存在大脑的这一部分。

智能体记忆也可以采用类似的分工。智能体的大量工作会保存在日志或会话记录中。Letta 和 UC Berkeley 的研究者提出了 sleep-time compute，让模型利用交互之间的空闲时间，重新组织已有上下文。同样的思路也可以帮助智能体整理记忆。它们可以回顾日志，纠正错误，或生成新的笔记和表示。这一过程通常称为 dreaming（图 1）。

我们发现，dreaming 是帮助 Claude 获得有效记忆的一种实用工具。本文将介绍我们对智能体记忆的理解，并逐一说明用于探索智能体记忆的几项评估。这些评估包括 dreaming 的使用，以及各个组成部分对记忆组织的贡献。

记忆笔记

我们所说的“智能体记忆”，是指 Claude 从经历中获得的知识。这些经历包括与用户的交互，以及被分配的任务。知识以可供日后读取的上下文形式保存，并在会话之间保留下来。这个定义不包括模型学习或管理上下文的其他方式，例如权重变化，即训练期间设定的内部参数发生改变；上下文学习，即在单次对话中获得知识；以及上下文压缩，即 Claude 编写摘要来替代较早的对话轮次，从而在新的上下文窗口中继续工作。

在人脑中，经历发生之前、期间或之后释放的化学信号，可以将某段记忆标记为重要。在离线阶段，被标记的记忆通常比未被标记的记忆重放得更频繁。这个称为重放（replay）的过程，有助于稳定这些记忆，并将它们整合进长期记忆。

类似地，Claude 可以在重要事件发生时，就在会话日志中为其添加标记，以便日后查找。它也可以将这些事件写入记忆存储，例如一个保存记忆笔记的文件夹（图 2）。但在还不知道接下来会发生什么时，Claude 怎么判断当下哪些信息值得记住？

记忆可以是对未来需求的预测

有时，记忆是一种预测。智能体写下一条规则，就是在预测这条规则描述的模式将来还会有用。例如，记下一项经过核实的事实，就是在预测未来某次会话中的智能体会希望直接依赖这项事实，而不必再次检查。随着时间推移，Claude 在做出这类预测方面已经进步了很多。

以 Continual Learning Bench（CL-Bench）1.0 中的一项任务为例。这个 benchmark 衡量智能体利用记忆处理长程任务的能力。其中一项任务要求 Claude 查询数据库，回答一系列问题。Claude 每给出一个答案，都会被告知正确解答，并可以写下记忆，帮助回答后续问题。

在这里，记忆可以支撑一个学习闭环。如果 Claude 答错了问题，它可以记录失败，提出关于错误原因的猜想，检验这些猜想，再把发现转化为指导后续回答的规则。

我们使用 Claude Managed Agents 运行了这项 CL-Bench 1.0 任务。Claude 回答每道题时都从一个新会话开始。唯一保留下来的资源，是一个在会话之间持续存在的记忆目录，Claude 可以从中检索文件。

不同模型在建立自身学习闭环方面，取得的成效不同。Claude Sonnet 4.6 能做到的是提出关于答案为何出错的猜想。它的记忆目录里散落着一些文件，每个文件都列出了若干未经检验的猜测。

Claude Opus 4.7 将笔记整合成了一份参考文档，并开始标明哪些事实已经核实，哪些仍未确认。Claude Sonnet 5 会在评分器检查答案后，将每个答案标为已确认。如果答错了，它还会写下更正。

Claude Opus 5 是这些模型中第一个完成闭环的模型。它的大多数条目都包含一条规则，以及它如何知道这条规则成立。此外，条目还包括先前问题的答案，以及对过程中发现的陷阱的明确提醒（图 3）。

与 Opus 5 一样，Claude Opus 5.5 和 Claude Sonnet 5.5 都完成了这个闭环。它们通过记忆保存经过验证的规则，以便更好地回答后续问题。使用记忆后，两者的得分都与 Opus 5 大致相同。不过，它们在不使用记忆时的基线表现略高。

Claude 已经学会判断什么值得记住

我们还通过让 Claude 玩 Pokémon Red，评估它判断哪些内容应保存到记忆中的能力。这个游戏要求 Claude 处理复杂的长程任务。每次运行开始时，我们都会给模型一个记忆文件夹。模型可以在游戏过程中读取和写入其中的文件（图 4）。

我们分别选取 Claude Sonnet 3.7 和 Claude Fable 5 的一次运行，对比它们在游戏进行约 10,000 步时的记忆文件夹。一个明显差异是，它们对什么值得记住的判断不同。Sonnet 3.7 假定所有内容都可能重要，因此不加区分地写入记忆。它的记忆文件夹像一份遭遇档案，常常为每场战斗、每件找到的物品、每个遇到的非玩家角色单独建一个文件。最终，Sonnet 3.7 在 225 个文件夹中写了 413 个记忆文件，并获得了一枚徽章。徽章代表玩家在游戏中的进度。

相比之下，Fable 5 在两个文件夹中写了九个文件，另加一个名为 global.md 的顶层文件，并获得了四枚徽章。

Sonnet 3.7 的做法之所以有问题，主要是因为 Pokémon 的游戏状态不断变化。它保存的详细记录也因此不断过时。随着游戏推进，Claude 必须花越来越多的时间和资源梳理记忆，而不是继续玩游戏。例如，在大约第 10,000 步时，Sonnet 3.7 开始建立第四个“主”记忆文件夹。接下来的 17 步里，它创建了六个文件，删除了另外九个，却没有在游戏中采取任何行动。

Fable 5 则用记忆保存游戏没有明确告诉它的内容。Sonnet 3.7 写入记忆的一些信息，例如玩家有多少钱、位于地图上的什么位置，每一轮都能直接从屏幕读取。保存这些信息是重复劳动。相比之下，策略、计划和经过检验的规则，只有 Claude 自己推导后才会存在。如果 Claude 不把它们记下来，它们就会消失。

Fable 5 据此组织了自己的记忆。它的 global.md 文件相当于一个仪表盘，包含当前目标、预先写好的道馆挑战计划，以及模型自己制定的记忆使用规则。道馆是赢得徽章的挑战场所。locations 文件夹保存特定路线的导航计划。gameplay 文件夹保存根据游戏机制知识总结出的策略。例如，在连续七个 Poké Ball 都未能捕获 Magikarp 之后，Claude 写道：“如果连续 3 个以上球都失败，就改变时机，在菜单步骤之间额外按几次‘等待’；这么做之后，紧接着就捕获成功了。”Magikarp 是最容易捕获的 Pokémon 之一。

Fable 5 的记忆文件夹小得多，但游戏进度比 Sonnet 3.7 远得多。Opus 5.5 采取了类似做法：它保留一个小型记忆笔记文件夹，记录当前目标和下一步行动，并在游戏过程中不断重写这些笔记。最终，它通关了游戏。

引导 Claude 写入记忆

我们发现，告诉 Claude 记忆的用途会有帮助，但不必告诉它具体该怎么用。在 CL-Bench 上，我们只是告诉 Claude 有一个记忆文件夹可用。这样的一般性指引，就足以让 Opus 4.7 和 Opus 5 有效使用记忆，并让两者的表现明显提升（图 3）。

我们还测试了给模型明确规则，规定应该向记忆中写入什么内容。每次测试只设置一条规则。我们比较了设置规则和不设置规则时，各模型从记忆中获得的收益。当规则是“只记录失败”时，Opus 5 和 Opus 4.7 都失去了记忆带来的大部分性能提升（图 5，右）。对于能力更强的模型，让它们自行判断什么值得记住，比提前设定固定规则更有效。这些规则甚至可能削弱表现。

我们还注意到，引导对较早的模型帮助最大。例如，Sonnet 4.6 经常不读取记忆目录中的文件，也不会检验自己对错误原因的猜想。

在这种情况下，提示 Claude 在回答前读取记忆文件，再明确检验自己的猜想，几乎让它的 benchmark 得分翻了一倍（图 5，左）。Sonnet 5 则会自行这样做。在没有相应提示的情况下，它每回答 10 次，就有 9 次会先读取记忆。相比之下，Sonnet 4.6 这样做的比例不到一半。

对于最先进的 Claude 模型，我们通常只给简单指引：当用户要求记住某件事，或某件事显然值得记住时，就创建记忆笔记。具体判断由 Claude 自己完成。

dreaming 可以纠正记忆

Claude 根据会话中对重要性的判断来写入记忆。因此，一条笔记如果从一开始就是错的，或随着环境变化逐渐偏离事实，Claude 在后续会话中仍可能读取并信任它。

dreaming 让 Claude 能够对照原始会话记录检查笔记（图 6）。我们曾用 Managed Agents 让 Claude 玩 Pokémon，并挂载了一个目录来保存记忆。在这次运行中，我们观察到了一个正面案例。

在游戏的某个阶段，玩家必须穿过 Mt. Moon。这是一组洞穴，入口在地图西侧，出口在东侧。入口附近有一个陷阱：一道只能单向跳下的台阶。玩家跳下后，会落回之前来的路线，而且没有明显的办法爬回去。Claude 把山口处的一栋建筑 PokéCenter 当作地标。因此，它会不会走下台阶，取决于它认为 PokéCenter 位于山的哪一侧。

某个时刻，Claude 错误地记下了 PokéCenter 位于东侧。走出 PokéCenter 时，它宣布：“Mt Moon 已经在我身后了。”随后又更新笔记：“Mt Moon 已完成。”但它其实并没有穿过 Mt. Moon。几次操作之后，Claude 跳下台阶，回到了来时的路线（图 7）。它的导航工具没有显示这次落差。因此，Claude 得出结论：“我向西走过头了。”它还以为自己此前一直在正确的一侧。事实并非如此。

接着，我们测试 dreaming 能否帮助 Claude 避开这个陷阱。我们对那个错误记录了 PokéCenter 位置的记忆文件夹运行了 dreaming。Claude 对照会话记录检查笔记，发现错误，并重写了笔记。会话记录为 Claude 提供了核验记忆的事实依据。有了纠正后的记忆笔记，Claude 直接返回 Mt. Moon，并最终到达 Cerulean City。

在使用未纠正笔记的运行中，Claude 三次跌回先前那条路线。第三次失败后，Claude 似乎放弃了，写道：“我要停下来，不再继续打转。”我们的实验设置自动回复，要求它继续。于是它继续前进，一路回到了山前的小镇 Pewter City，希望在那里恢复状态、补充物资。这次运行结束时，Claude 始终没有到达 Cerulean City。

dreaming 可以构建新的记忆表示

借助 dreaming，Claude 可以构建帮助浏览记忆的表示（图 9）。它使用的一种记忆表示称为 wiki。这是由 Claude 编写和维护的一组页面，汇集它对某一主题的了解，并链接到其他笔记。这些链接实际上为 Claude 提供了一张地图，让它能够梳理记忆，并在需要时高效定位相关内容。

随着知识库不断增长，wiki 这样的表示可以帮助 Claude 在其中查找信息。我们使用 Stainless 的一批内部文档，探索了 wiki 作为记忆表示的作用。Stainless 是我们在 5 月收购的一家软件公司。这批语料约有 350,000 个文件，约合 4.2 亿 token。我们围绕这批语料创建了一组包含 25 道问题的评估，并为 Claude 提供搜索工具，让它探索这些文档。我们还要求 Claude 通过 dreaming，依据这些文件构建 wiki。在 128 次会话中，我们提示 Opus 5 智能体探索文件、编写或修正相互链接的 wiki 页面、合并重复内容，并对照来源核验陈述。

每次会话都接续此前会话中智能体取得的进展，并通过共享日志协调工作。当我们把 dreaming 从两次会话扩展到 128 次时，在这 25 道问题上的评分标准达成率从 13% 提高到了 48%（图 10）。

Claude 以渐进方式构建 wiki。创建初版 wiki 后，它会在后续几轮 dreaming 中进行增补、编辑或删减。在最初几轮 dreaming 中，Claude 的知识状况像一名新员工。仅凭 wiki 回答问题的能力还很有限。dreaming 越多，它的知识地图就越丰富，逐渐像一名经验丰富的员工。在测试中，我们发现，同时提供搜索工具时，wiki 对 Claude 的帮助最大。在搜索与 wiki 结合使用的情况下，随着 wiki 扩展，Claude 的综合得分从 54% 提升到 61%。相比之下，仅提供搜索工具时，得分为 53%。仅用 wiki 回答问题时，Claude 的最高得分为 48%。同时使用搜索与 wiki，还让每道题节省了约 20,000 token。

我们希望测试，哪些类型的任务能从 Claude 拥有 wiki 中获益。为此，我们使用了 Harvey LAB benchmark，以及一组与某次并购有关的文档。这个 benchmark 向 Claude 提供一组文档，要求它根据文档内容生成法律简报，再依据一组标准为简报评分。这些评估或许不如玩一局 Pokémon 有趣，但它们为我们提供了多样化的文档集合，可用于构建 wiki。

我们要求 Claude 根据文档构建 wiki。随后，我们分别让 Claude 借助 wiki 和直接文件搜索来回答并购问题，或生成 LAB benchmark 所要求的法律简报。其中一项测试提出了 24 道并购相关问题（图 11，左）。超过一半的问题需要 Claude 查找多份文档中的信息，其中许多还需要做判断或计算。在这些题目上，也就是红线和橙线所代表的题目，Claude 查阅 wiki 时得分为 87%，仅使用搜索时为 73%。

在其他情况下，wiki 的帮助较小。在一项 LAB 任务中（图 11，右），简报评分标准所需的信息通常可以通过文本搜索，从单份文档中找到。与搜索相比，wiki 没有显示出明确的性能收益。在另一项 LAB 任务中，wiki 的体积超过了文档本身（图 12）。这让人想到 Borges 的一段式短篇小说《论科学的精确性》（“On Exactitude in Science”）：制图师绘制了一张极其详细的地图，大到与它描绘的帝国一样大。Claude 也做出了一份极为详尽的 wiki，却几乎没有形成任何抽象。

dreaming 可以将笔记提升到记忆层级的上层

dreaming 也可以把笔记提升到记忆层级的顶部。智能体运行框架随后可以在每次会话开始时，预先把这些笔记加载到 Claude 的上下文中（图 13）。这样，Claude 就不必搜索这些笔记，甚至不必先意识到有什么需要搜索。

把记忆带入新会话是一种上下文注入（context injection），需要谨慎处理。注入的记忆会占用宝贵的 token，而错误笔记可能被带入每一次会话。加载笔记也不保证 Claude 会照着行动。我们的 Claude Code 文档提醒，指令文件越长，指令遵循程度就越低。因此，记忆层级的最上层必须保持相对精简。dreaming 在这里的一项主要工作，就是把部分细节下移到较低层级，同时留下链接，以保持顶层精简。

Claude Code 的 auto memory 也用同样的方式控制注入层的大小，由 Claude 在会话期间维护。Claude 不会将全部 auto memory 加载到每次会话的上下文窗口中。它只加载 MEMORY.md 的前 200 行或 25 KB。这个文件头部充当索引，告诉 Claude 它知道什么，以及去哪里查找。

dreaming 可以让记忆围绕特定目标发展

dreaming 也可以影响记忆的增长方式。例如，Claude Duet 这样的助手，通常会受益于围绕所服务用户组织的记忆。dreaming 可以经过调整，让记忆的构建服务于某个特定目标。

指导记忆如何增长的指令，会随任务而变化。这些指令告诉 Claude 哪些信息真正重要。例如，LAB benchmark 中有一项任务模拟公司收购，并提供一组合同。简报的评分依据，是它是否准确描述了合同条款。

起初，我们使用基本指令生成 wiki，没有告诉 Claude 该如何使用它。这项任务高度依赖合同条款。在构建 wiki 时，多个智能体同时向一张共享的合同条款表写入内容（图 14，左）。

结果，wiki 缺失了一些关键事实。我们为基于该 wiki 生成的简报评分时，发现 Claude 只纳入了 57 项事实中的 41 项，即 72%。调查原因后，我们发现，共享表格对合同条款的概括不佳，有些条款甚至完全缺失。原因是智能体覆盖了彼此的工作。

合同条款是这份 wiki 最重要的部分，但指令没有说明这一点。为了找到更好的指令，我们运行了一个循环：让 Claude 反思失败，提出指令修改方案，再重新构建 wiki。这个循环让 Claude 发现，准确遵循合同条款至关重要。它据此重写了构建 wiki 的指令。

每份合同都获得了自己的 wiki 页面，由一个智能体编写。页面逐字引用条款，而不是把条款概括到一张共享表格中。我们为依据改进后 wiki 生成的简报评分时，发现能够满足 100% 的评分标准，高于此前的 72%。

dreaming 可以补上单次会话留下的缺口

Claude 写记忆笔记时，只能看到那一次会话中的上下文。dreaming 可以跨多个会话搜索，发现共同模式，或纠正常见错误。

在为 LAB benchmark 构建 wiki 时，例如图 14 所示的案例，Claude 有时会链接到尚未创建的页面。第二轮 dreaming 补上了许多这样的缺口。在一项任务中（图 15），dreaming 发现了九条指向 wiki 中缺失页面的链接，并把它们重新指向了同一文档已有的页面。它还新增了三个页面，其中包括一个索引，以完善 wiki。

回顾过去，展望未来

如何为智能体设计记忆系统，仍有许多开放问题。其中一个问题是，Claude 应该在什么时候创建记忆。执行任务时，Claude 可以向文件夹、文件或数据库等记忆存储写入内容。这样能在信息产生时就捕捉其重要性，让关键细节立即可供后续轮次或会话使用。但即时记笔记不可避免地会分散 Claude 对主要任务的注意力。相比之下，dreaming 可以把记忆创建转移到后台，但它的产出未必能立即供 Claude 使用。

另一个问题是，如何可靠地保持记忆更新。Claude 可能做出错误预测，也可能把从一开始就不正确的规则写入记忆。随着环境变化，记忆还可能逐渐偏离事实，变得不再相关。dreaming 是纠正这些错误的一种方式（图 8），但它需要计算资源。要求 Claude 持续检查所有记忆，可能并不现实。因此，重要的做法可能是让 dreaming 聚焦于容易变化的信息，或精细调整 dreaming 的频率，例如根据记忆被访问的频次进行调整。

将会话记录搜索作为 Claude 记忆的基础，也是一种合理思路。有时，把 wiki 等表示与搜索结合起来会很有效（图 10）。但 Claude 需要投入计算资源来维护这些记忆表示，确保其中不会不断累积错误或幻觉。

尽管 Claude 对什么值得记住的判断已经改善，但没有模型能够真正知道未来的对话轮次会发生什么。dreaming 让 Claude 有机会回顾过去，并投入计算资源来整理记忆、纠正错误、维护记忆表示，让后续会话更容易访问记忆。随着 Claude 能力增强，记忆系统也会继续演进。对于如何设计 Claude 的记忆系统，我们仍有很多需要学习的地方。
