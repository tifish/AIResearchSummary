这些结果说明，提示词大幅缩短，不等于总成本同比例下降。判断优化收益，必须先看它影响的是哪部分开销。

模型能力提高后，可以减少反复指导

早期模型需要详细的工具用法和工作流程指令。能力提高后，Cursor 发现，只需说明工具如何工作，多个模型家族通常就能正确使用。

系统提示词因此缩短了约 66%。这表明，模型进步也能通过减少每轮上下文，带来间接的效率收益。

工具出现频率低，不代表可以直接隐藏

Cursor 保留了读取、搜索、编辑和 shell 等高频工具。部分模型容易凭空调用 ask_question，因此它也继续保留在静态上下文中。

Plan Mode 中的 create_plan 同样需要保留。按需加载必须兼顾模型行为和产品流程，不能只按使用频率划线。

缓存优化需要同时处理边界和内容稳定性

  1. 稳定内容放在前面工具和系统指令只承载很少变化的内容。
  2. 为稳定层设置断点按原文所述，自 GPT-5.6 起，Cursor 利用显式缓存断点标记可复用前缀。
  3. 变化内容放到后面skills、子智能体和环境信息等内容移入“隐式用户消息”，位于缓存边界之后。

冷缓存未命中率因此下降了20%。关键不只是开启缓存，还要让可复用的请求前缀保持稳定。

子智能体能节省上下文，也会增加协调成本

子智能体通常从新的上下文窗口开始。主智能体收到结果后，无需携带其全部工作过程。但上下文隔离也可能导致重复劳动，或继续执行已经没有必要的任务。

Cursor 移除了强烈鼓励用子智能体探索代码库的指令。它还限制了子智能体改用其他模型的条件：只有用户或 harness 明确指示时才这样做。效率取决于是否恰当地委派，而不是委派次数越多越好。

最值得带走的洞见

  • 长任务需要持续管理上下文。每轮重复携带的内容，会逐渐成为显著成本。
  • 能力可用，不必等于定义常驻。工具按需加载能减少静态负担，但要保留必要的调用入口。
  • 真实流量是重要检验标准。Cursor 用 A/B 测试观察成本、延迟和错误等指标。原文指出，偏重难题的评测未必代表用户请求的真实分布。
  • token 增长慢于工作量，是未来目标。目前报告的是成本下降 7%。长期增长关系仍是 Cursor 的预期。

过去几个月，我们通过提高 Cursor 智能体运行框架（harness）的效率，来应对这一变化。借助 harness，我们可以直接控制每个请求的组装方式、上下文的复用方式，以及何时在多个智能体之间分配工作。这几个层面的调整，在未降低智能体质量的情况下，让用户的 token 成本下降了 7%。

精简系统提示词

在每一轮中，模型开始工作之前，Cursor 都会提供一些上下文。其中包括系统提示词，以及智能体可用工具的定义。这些上下文贯穿整段对话。因此，在我们能够完全控制的开销来源中，它已经成为占比最大的一部分之一。

模型能力较弱时，我们必须详细说明如何使用工具、管理任务，以及执行代码修改流程。我们还必须防范一些奇怪的行为，例如输出极长的哈希值、二进制内容或表情符号。

随着模型能力提高，许多指导已经不再必要。我们不必再列出长长的指令清单，反复强调“不要这样做”“你必须”或“重要”。只要说明工具如何工作，模型通常就会遵循。这一点在不同模型家族中都成立，使我们能够将系统提示词缩短约 66%。

随着时间推移，新模型需要新的指导，我们也会继续增删指令。这些指导随后会进入未来模型的训练。要针对真实流量有效优化 harness，在大量用户中开展 A/B 测试至关重要。评测可以快速提供有用的参考，但它们往往侧重“难题”，无法准确反映用户请求的真实分布。

仅在需要时加载工具

系统提示词只是 Cursor 每轮提供的上下文的一部分。另一部分是工具定义。随着我们在这一年里为 Cursor 智能体加入更多强大功能，工具定义也大幅增加。这些功能包括后台 shell 监控、云端子智能体，以及更可靠的网页内容访问。大多数工具都很重要，但每种工具需要用到的会话占比都不足 20%。

这给提高效率留下了空间：工具可以保持可用，却不必在每个请求中都附上完整定义。今年早些时候，我们已经解决过类似问题。当时，我们把 MCP 工具移入动态上下文，只在需要时加载。在调用过 MCP 工具的会话中，这项调整使总 token 数减少了 46.9%。

现在，我们将同样的方法应用到了自己的内置工具上。

为了决定哪些工具应留在静态上下文中，我们根据各工具的使用频率，以及模型是否需要从一开始就看到它们，对多种配置进行了 A/B 测试。我们跟踪了 token 用量、成本、延迟、工具调用错误，以及智能体的整体使用情况，以确保节省开销不会降低质量。

改善缓存复用

减少每个请求中的静态上下文后，我们进一步提高了跨轮次缓存重复上下文的效率。

智能体每一轮都会重新发送一个很长的请求。其中包含工具、系统指令、初始化信息，以及迄今为止的对话。相邻两轮之间，请求开头的大部分内容保持不变，而末尾的对话则持续增长。

提示词缓存让模型提供商可以复用这段未发生变化的前缀。不过，不同提供商允许配置缓存的程度可能不同。在 GPT-5.6 之前，缓存边界会根据最新请求自动确定。虽然工具和系统指令很少变化，但它们没有被清晰地单独标记为可复用内容。

自 GPT-5.6 起，OpenAI API 除了默认的隐式缓存，也允许客户端标记显式缓存断点。我们现在会在请求中稳定的内容层之后、持续增长的对话之前设置断点。这样，后续轮次就能复用更多未发生变化的前缀。

只有前缀本身保持稳定，断点才能发挥作用。因此，我们也更严格地控制请求最前面放置的内容。我们让工具和系统指令只包含很少变化的内容，并将变化较多的初始化信息移到缓存边界之后，放入我们称为“隐式用户消息”（phantom user message）的部分。这里承载与用户和请求相关的上下文，例如 skills、子智能体和环境信息。

这些调整使冷缓存未命中率下降了 20%。

压缩文件读取内容

另一个主要的 token 开销来源，是智能体工作过程中添加的上下文。其中很大一部分来自文件读取。

Cursor 智能体通过 Read 工具读取文件。过去，这个工具会为每一行标注行号。原因是模型不擅长自行计算行数，而它们又需要向用户引用具体的代码片段。

单个行号只占大约 3—5 个 token。但当智能体在一次会话中读取数万行内容时，为每一行编号就会增加相当可观的上下文。

我们改为只在每十行标注一次行号，以降低这部分开销。这个标注频率仍足以让模型正确引用代码。这项调整使缓存读取 token 减少了 1.6%，质量没有下降。

有策略地使用子智能体

智能体运行时间变长后，会有更多机会把工作委派给子智能体。这可以减少 token 开销，因为每个子智能体通常从一个新的上下文窗口开始，而不必携带主智能体的完整对话。子智能体报告结果后，主智能体就能继续工作，无需携带子智能体的全部工作上下文。

不过，智能体与子智能体之间的这种上下文隔离，也会带来协调成本。由于它们不共享上下文，可能会重复工作，或者执行已经没有必要的任务。

我们做了两项调整，以获得效率收益，同时避免增加不必要的协调。首先，我们移除了强烈鼓励智能体使用子智能体探索代码库的指令。随着子智能体在训练数据中越来越常见，研究人员也将其纳入后训练，模型本身已经学会了这种模式。移除额外提示后，子智能体的使用变得更加均衡。

我们还收紧了子智能体选择模型的方式。Cursor 可以使用任何可用模型来创建子智能体。这让我们能够利用不同模型相互弥补盲点，也可以让昂贵的模型负责规划，再由更便宜的模型负责实现。我们更新了工具参数，让智能体只有在用户或 harness 明确指示时，才选择不同的模型。

持续提高 harness 效率

我们会继续测量上下文在长时间运行中如何积累，并测试 harness 可以在哪些环节减少重复处理，同时不影响智能体质量。随着时间推移，我们预计，这将让 token 用量的增长速度远低于智能体可完成工作量的增长速度。我们也把这些经验应用到了 Grok Bot。我们正在优化它独有的 harness，让用户能够以最低成本完成尽可能多的工作。
