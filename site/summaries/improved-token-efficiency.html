单项降幅看似不大，但它们作用在长对话的每一轮上，叠加后才形成整体成本下降。

模型变强，提示词可以变短

早期模型需要详细的工具用法和流程指令。还要专门防止超长哈希输出、二进制输出和 emoji这类怪异行为。

现在只需说明工具怎么工作，各模型家族通常都会遵守。于是系统提示词砍掉了约 66%。

用线上 A/B，而不是只看评测

Cursor 强调：评测是快速有用的代理指标，但往往偏向“难题”。

它们不能反映真实用户请求的分布。因此工具保留方案、提示词增删都要在大规模用户上 A/B 测试，同时盯住成本、延迟、工具调用错误和使用量。

提示词中的“护栏”是有保质期的。模型换代后应主动回收，否则它们会成为每轮都要付费的历史包袱。

缓存 · 让前缀保持稳定

把请求切成“不变的前半段”和“变长的后半段”

每轮请求都会重发工具、系统指令、初始设置和全部对话。开头基本不变，末尾持续增长。

工具定义只放很少变化的内容

GPT-5.6 之前，缓存边界由系统根据最新请求自动判断，稳定层没有被单独标为可复用。GPT-5.6 起，OpenAI API 支持显式缓存断点。Cursor 把断点放在稳定层之后，并把易变内容挪到断点后面。结果是冷缓存未命中率下降 20%。

断点只是工具，真正起作用的是“把会变的东西挪出前缀”这条纪律。

文件读取：行号也是成本

Read 工具原本给每一行编号。原因是模型不擅长自己数行，又需要向用户引用具体位置。

单个行号只占约 3–5 个 token。但一次会话要读数万行，累积起来就很可观。

改成每十行一标后，模型仍能准确引用代码。缓存读取 token 下降 1.6%，质量没有下降。

子智能体 · 收益与代价

子智能体不是越多越省

机会：上下文隔离

子智能体通常从全新上下文窗口开始，不必带着父智能体的完整对话。汇报结果后，父智能体也无需背负它的工作过程。

风险：协调成本

不共享上下文的智能体可能重复劳动，或者去做已经不再需要的任务。

Cursor 的两项调整：

  • 删掉强推指令：模型已在训练和后训练中原生学会使用子智能体探索代码库，额外催促反而失衡。去掉后使用更均衡。
  • 限制换模型：子智能体可用任何模型，比如贵的规划模型配便宜的实现模型。但现在只有在用户或 harness 指示时才换。
当模型已经“学会”某种行为时，提示词里的鼓励会变成过度使用，需要反过来收一收。

最值得带走的洞见

随着智能体日趋成熟，开始承担更有野心的任务，token 花费的构成也发生了变化。智能体现在工作的时间更长。每一步都要把更多上下文带到下一步。因此，我们如何组装和管理这些上下文，变得越来越重要。

注：“系统与工具定义”包含压缩摘要（compaction summaries）。“用户文本”包含手动附加的技能（skills）。“技能与插件”包含技能描述、MCP 工具描述，以及放入静态上下文的规则。

过去几个月，我们针对这一变化，改进了 Cursor 智能体 harness 的效率。harness 让我们能直接控制三件事：每个请求如何组装、上下文如何复用、何时把工作分给多个智能体。在这些层面上的改动，让用户的 token 成本降低了 7%，而智能体质量没有下降。

精简系统提示词

在每一轮智能体交互中，模型开始工作之前，Cursor 都会先提供一些上下文。其中包括系统提示词，以及智能体可用工具的定义。这些上下文贯穿整段对话。因此，它已成为我们能完全掌控的最大花费来源之一。

在模型能力较弱的时候，我们必须把工具用法、任务管理和代码修改流程的指令写得明明白白。我们还得防范一些怪异行为，比如超长的哈希值输出、二进制输出和 emoji。

随着模型进步，这些指引大多变得多余。我们不再需要一长串“不要这样做”“你必须”“重要”之类的指令。只要定义清楚工具的行为，模型通常就会遵守。这一点在不同模型家族中都成立，于是我们把系统提示词精简了约 66%。

随着时间推移，我们会持续增删指令。新模型会需要新的指引，而这些指引又会进入未来模型的训练。要针对真实流量有效优化 harness，在大规模用户群体上做 A/B 测试至关重要。评测（evals）可以作为快速且有用的代理指标。但它们往往代表的是“难”题，无法恰当反映用户请求的真实分布。

按需加载工具

系统提示词只是 Cursor 每轮提供的上下文之一。另一部分是工具定义。今年以来，我们为 Cursor 智能体加入了更强大的能力，工具定义也随之大幅增长。这些能力包括后台 shell 监控、云端子智能体，以及更可靠的网页内容访问等。这些工具大多很重要，但每一个都只在不到 20% 的对话中用到。

这带来了一个提升效率的机会：让工具保持可用，但不必在每个请求中都附上它们的完整定义。今年早些时候，我们解决过类似的问题。当时我们把 MCP 工具移入动态上下文，只在需要时加载。在调用过 MCP 工具的会话中，这让总 token 数减少了 46.9%。

现在，我们把同样的技术应用到了自己的内置工具上。

为了决定哪些工具保留在静态上下文中，我们 A/B 测试了几种配置。依据是每个工具的使用频率，以及模型是否需要从一开始就看到它。我们跟踪了 token 用量、成本、延迟、工具调用错误和整体智能体使用情况，确保节省下来的成本不以质量下降为代价。

最常调用的工具 至少调用过一次该工具的智能体对话占比

最终，我们把读取、搜索、编辑和使用 shell 这些高频工具保留在静态上下文中。我们还保留了 ask_question，因为一些模型容易幻觉出对它的调用。对特定产品流程至关重要的工具也被保留，例如 Plan Mode 中的 create_plan。其余工具现在都在智能体需要时才加载。

提升缓存复用

减少了每个请求中的静态上下文之后，我们又改进了重复上下文在各轮之间的缓存效果。

每一轮，智能体都会重新发送一个很长的请求。其中包含工具、系统指令、初始设置，以及到目前为止的对话。请求开头的大部分内容在各轮之间保持不变，而末尾的对话则在持续增长。

提示词缓存（prompt caching）让模型提供商能够复用这段不变的前缀。不过，不同提供商在缓存可配置性上有所差异。在 GPT-5.6 之前，缓存边界是根据最新请求自动确定的。尽管工具和系统指令很少变化，它们本身并没有被清晰地标记为可复用。

从 GPT-5.6 开始，OpenAI API 允许客户端在默认的隐式缓存之外，标记显式的缓存断点。现在，我们把断点放在请求的稳定层之后、不断增长的对话之前。这样，后续轮次就能复用更多不变的前缀。

断点只有在前缀本身保持稳定时才有用。所以我们也收紧了每个请求开头放置的内容。具体做法是：工具和系统指令只留给很少变化的内容；把更多易变的初始设置移到缓存边界之后，放进我们的“幻影用户消息”（phantom user message）。这条消息承载与用户和请求相关的上下文，比如技能、子智能体和环境信息。

这些改动让冷缓存未命中率降低了 20%。

压缩文件读取

token 花费的另一大来源，是智能体在工作过程中不断加入的上下文。其中很大一部分来自读取文件。

Cursor 的智能体通过 Read 工具读取文件。这个工具传统上会给每一行编号。原因是模型自己不擅长数行，又需要为用户引用具体的代码片段。

单个行号只占大约三到五个 token。但当智能体在一次会话中读取数万行时，给每一行编号就会增加相当可观的上下文。

为了降低这部分开销，我们改为每隔十行才标一个行号。这个频率仍然足以让模型准确引用代码。这一改动让缓存读取 token 减少了 1.6%，质量没有任何下降。

有策略地使用子智能体

智能体运行得越久，就越有机会把工作委派给子智能体。这可以降低 token 花费。因为每个子智能体通常从全新的上下文窗口开始，而不是携带父智能体的完整对话。子智能体汇报结果后，父智能体可以继续工作，而不必背负子智能体的完整工作上下文。

不过，智能体与子智能体之间的这种上下文隔离，确实会带来一笔协调成本（coordination tax）。不共享上下文的智能体可能重复劳动，或者去做已经不再需要的任务。

为了获得效率收益、又不增加不必要的协调，我们做了两项改动。第一，我们删除了强烈鼓励智能体用子智能体探索代码库的指令。子智能体在训练数据中越来越普遍，研究人员也把它们纳入了后训练，模型已经原生学会了这种模式。去掉额外的提示后，子智能体的使用变得更加均衡。

我们还收紧了子智能体选择模型的方式。Cursor 可以用我们提供的任何模型来生成子智能体。这样既能弥补不同模型的盲点，也能把昂贵的规划模型与更便宜的实现模型搭配使用。我们更新了工具参数，使智能体只有在用户或 harness 指示时，才会选择不同的模型。

持续提升 harness 效率

我们会继续测量上下文在更长的运行中如何累积，并测试 harness 在哪些环节可以减少重复处理，同时不影响智能体质量。长期来看，我们预期这将让 token 用量的增长远远慢于智能体所能完成的工作量的增长。我们也把这些经验带到了 Grok Bot。我们正在优化它独特的 harness，让用户以最低的成本完成最多的工作。
