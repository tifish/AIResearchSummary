Cursor Router 如何为任务选择合适的模型

How Cursor Router chooses the right model for the task

一句话总括：Cursor 把模型路由变成了一个由真实开发流量驱动的决策系统，同时学习任务复杂度、模型优势、用户满意度和实际成本。

41% Auto Balance 的满意度超过 Opus 4.8，成本低 41%。同期满意度又提高了 3%。
96% Compass 认为最可能成功的任务，最终获得正向表现信号的比例。

真实使用行为，而非静态榜单

Cursor Router 的核心判断不是哪个模型在 benchmark 上总分最高。它关注模型在真实开发任务中的实际表现。

训练数据来自数十万轮真实 Cursor 流量。每条数据都保留当轮上下文、可供路由器使用的信号，以及表现和成本两个结果。

为什么这会改变理解？

模型切换可能造成缓存失效。真实 token 用量也会偏离 benchmark 环境。把这些成本纳入数据后，“最强模型”不再自动等于“最佳选择”。

路由分成两个问题

1. Compass 估算复杂度

它预测用户是否会满意，并给出 0 到 1 的连续分数。

→
2. 阈值决定是否升级

简单任务留给低成本模型。复杂任务进入前沿模型路由。

→
3. 分类体系匹配模型

系统结合领域、任务和修饰特征，选择历史表现最合适的模型。

Compass 最低置信组的正向表现比例仍有 71%，最高组则达到 96%。这说明分数能有效区分难度，但它衡量的是成功概率，而不是一道绝对的难题判定线。

离线筛选，线上定论

团队先用交叉验证调整 Compass 阈值和成本预算，再用未参与训练的保留测试集评估候选策略。

但离线数据无法完整模拟 token 使用、缓存和模型切换。最终判断仍来自真实开发流量。

持续适应模型前沿

Cursor 已把 Opus 5 加入候选模型，并改进 Compass。长期目标是持续预测每个模型的质量和成本，再根据生产结果自动更新。

最值得带走的洞见

复杂度判断与模型选择应当分开 先决定是否值得升级，再决定升级到谁。两阶段设计让成本和质量更容易控制。
用户下一步行为可以成为质量信号 用户转向下一项任务是正向信号。用户纠正代理则是强负向信号。
没有一个模型统治所有任务 模型的优势与任务类型有关。按类别学习优势，比维护固定优先级更有效。
生产环境才是路由策略的最终考场 缓存失效、实际 token 用量和模型切换成本都会改变结果。离线评估只能筛选候选方案。

7 月 22 日，我们推出了 Cursor Router，并带来两种新配置：Auto Intelligence 和 Auto Balance。此后，随着新模型陆续出现，以及路由系统从更多生产流量中学习，我们一直在改进这两种模式。

如今，Auto Intelligence 的用户满意度已超过 Fable 水平，成本则低 68%。与发布时相比，成本又降低了 18%。Auto Balance 的表现超过 Opus 4.8，成本低 41%。同期成本又降低了 8%，用户满意度还进一步提高了 3%。

我们正在构建一个能随模型前沿共同进步的 Cursor Router。本文将解释当前系统的工作方式。

数据驱动的路由方法

Cursor Router 建立在这样一个理念之上：模型选择应该从模型处理真实开发工作的表现中学习，而不是根据 benchmark 分数推断。

路由器会利用当前轮次和近期对话状态中的信号来做出每一次决定。这些信号包括任务类别等结构化特征，也包括最近的工具调用和当前工作的整体上下文。

接下来，路由分为两部分。

首先，我们需要判断当前轮次是否足够简单，可以交给价格更高效的模型。我们的复杂度预测器 Compass 会做出这一判断。

其次，如果当前轮次要求更高，我们就要判断哪一个前沿模型最可能擅长这类工作。为此，我们会使用一套从真实开发流量中学习得到的任务、领域和修饰特征分类体系，对当前轮次进行分类。

构建数据集

为了开发路由系统，我们首先需要一个能够反映生产环境实际情况的数据集。我们使用真实 Cursor 流量构建了这个数据集，以保留开发任务的真实分布、每轮任务周围的上下文，以及模型切换带来的影响。

一如既往，在整个过程中，我们都尊重用户的隐私模式和数据保留设置。

该数据集包含数十万轮对话样本，覆盖多种模型。每个数据点都包括路由器当时可用的对话信号，以及用于比较路由选择的两个结果。

表现。我们根据用户接下来的行为推断模型表现。用户转向下一项任务，是一个很强的正向信号。用户纠正代理，则是一个很强的负向信号。

成本。我们根据 API 定价和该轮的 token 使用量计算成本。由于数据来自真实流量，它还能反映 benchmark 经常忽略的费用，包括模型切换导致缓存未命中而产生的成本。

使用 Compass 预测复杂度

Compass 通过预测用户是否会对 Cursor 的回复感到满意，来估算每一轮任务的复杂度。我们使用前面提到的表现信号训练它。

我们把最终预测结果作为复杂度的替代指标。这样做之所以有效，是因为用户很少会在提交代码等简单任务后要求修正。面对更复杂的工作时，用户提出后续要求的可能性会更高。

我们在线上评估了 Compass，并确认它的分数能够有力预测用户满意度。Compass 认为最有可能成功的任务，有 96% 获得了正向表现信号。它认为最不可能成功的任务，也有 71% 获得了正向表现信号。

Compass 分数可以预测用户满意度

在实际运行中，Compass 会给每一轮任务分配一个 0 到 1 之间的连续复杂度分数。我们在这个区间内设定阈值，以决定哪些任务继续使用价格高效的模型，哪些任务需要升级到前沿模型。阈值越低，留在价格高效模型上的流量越多。阈值越高，升级发生得越频繁。

学习各模型的优势

Compass 告诉我们某一轮任务是否复杂到值得使用前沿模型。接下来的问题是，应该使用哪一个前沿模型。

为了解答这个问题，我们根据真实开发流量建立了一套分类体系。它从三个维度描述每一轮任务：

  • 领域用于识别工作发生在哪里，例如后端、数据库 schema 和前端。
  • 任务用于识别开发者想完成什么，例如修复错误、运行命令和编写测试。
  • 修饰特征用于捕捉跨越领域和任务的特点。这些特点可能改变最合适的模型，例如范围明确的编辑、产品问题和高度依赖视觉的改动。

随后，我们会比较不同模型在这些类别中的表现。我们发现，没有一个模型能在所有工作类型上占据优势。每个模型都有自己表现更好的类别：

Grok 在广泛的日常工作中具有很高的性价比。它的推理成本较低，因此在 Git 命令和常规数据库操作等类别中尤其有效。

Sol 在规划和理解代码库方面表现出色。它在多种实现任务中也取得了良好结果，成本低于其他前沿模型。

Opus 擅长执行密集型工作。它在 DevOps、数据库查询和性能优化方面尤其突出。

Fable 擅长调试和视觉实现。对于复杂任务，它带来的质量提升最有价值，也足以证明更高成本的合理性。

Cursor Router 会利用这些差异，为每一轮任务匹配最合适的模型。

组合成算法

Compass 和分类体系承担互补的角色。Compass 估算当前轮次与模型无关的复杂度，再把分数与路由阈值进行比较。根据分数所处的位置，我们会把任务交给推理成本较低的 Grok，或者使用分类体系找出在这类工作中观察表现最强的前沿模型。

当 Compass 确实把某一轮任务交给分类路由器时，模型选择会遵循两条规则：

只有表现明确更好时才进行路由。候选模型只有在对应任务标签上的观察表现，通过了相对于价格高效模型的单侧 75% 提升阈值后，才有资格进入选择范围。粗略来说，这意味着我们需要有 75% 的把握，确认这种提升是真实存在的。

在预算内选择最佳组合。优化器会从符合条件的候选模型中，选择按流量权重计算的模型组合。这个组合需要在模式的预算范围内控制平均单轮成本，同时带来最大的预期表现提升。

Compass 阈值和任务路由器的成本预算共同决定了每种模式在成本与表现曲线上的位置。Auto Balance 会让更多流量留在价格高效路径上，并为任务路由器设置较小的预算。Auto Intelligence 则为任务路由器提供更大的选择空间。当预期表现提升足以证明成本合理时，它可以更多地使用前沿模型。

在生产环境中评估表现

我们分两个阶段评估路由策略。首先，我们使用交叉验证来调整 Compass 阈值和优化预算，避免对某个特定的数据划分过度拟合。随后，我们在训练期间从未使用过的保留测试集上评估选定的策略。

这样可以更可靠地估算每种策略在新流量上的表现。它也能帮助我们淘汰较弱的候选方案，并在部署前比较预期成本和表现。但离线分析仍无法完整反映策略在生产环境中的行为，benchmark 也有同样的局限。因此，真实开发流量仍是最具代表性的测试。

接下来，我们在真实流量上测试这些策略。在生产条件下，我们可以测量用户满意度，以及每一轮任务的实际成本。这种测试能够捕捉离线环境难以模拟的影响，包括 token 使用量、缓存和模型切换成本。

发布前，我们在真实流量上测试了两种模式。结果表明，与单独使用某一个前沿模型相比，两种模式都改善了成本与表现之间的权衡。Auto Balance 以更低的成本提供了高于 Opus 4.8 的满意度。Auto Intelligence 则以低得多的成本，达到了接近 Fable 的满意度水平。

此后，随着路由系统和可用模型不断改进，我们反复执行这一流程，让两种模式在成本与表现前沿之外继续向前推进。

紧跟模型前沿

Cursor Router 发布后，我们把 Opus 5 加入了路由候选范围，并改进了 Compass 的预测。这既为路由器提供了更强的模型组合，也让它能凭借更好的信号判断何时值得使用某个模型。

长期来看，我们希望路由器变得更加自适应。它将预测每个模型的预期质量和成本，从生产结果中学习，并持续更新。随着系统不断改进，Cursor 用户可以在最需要的地方获得前沿模型的能力，而不必为每一轮任务都支付前沿模型的价格。
