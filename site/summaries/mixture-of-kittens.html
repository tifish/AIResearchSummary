Mixture-of-Kittens：面向 NVL72 的开源 MoE 巨型内核

Mixture-of-Kittens: our open-source MoE megakernel for NVL72s

一句话总括：MoK 通过统一设计通信方向、计算流水和设备端缓冲区，把分布式 MoE 的主要瓶颈从一串割裂操作变成了一个确定性巨型内核。

瓶颈不只在矩阵乘法

在部分 Composer 训练配置中，MoE 层会占用超过一半的端到端训练时间。此前的 MXFP8、NVFP4 和 warp decode 优化主要改善计算，却把跨 GPU 通信留在内核之外。

MoK 的关键变化是把 dispatch、专家 FFN 和 combine 一起设计。性能问题由此不再被误解为单个算子的效率问题。

NVL72 改变了优化边界

一个 NVL72 机架把 72 块 GPU 放进同一 NVLink 域。这使细粒度的通信与计算重叠成为可能。

但 GB300 的 Grace CPU 相对 GPU 较慢。GPU 很容易追上 CPU 侧任务，因此设计必须尽量消除 CPU 工作和 CPU-GPU 同步。

通信方向不是统一答案

前向 dispatch拉取式
前向 combine推送式
反向 reverse-combine拉取式
反向 reverse-dispatch推送式

这组方向允许四次通信复用同一份只有数 MB 的调度表。它还消除了跨 GPU 的多通道完成信令。选择通信方向时，调度成本、双向链路利用率和信令延迟比“推送通常更快”的经验判断更重要。

过细和过粗都浪费硬件

通信粒度过细时，Tensor Core 会频繁等待。粒度过粗时，首批 token 到达太晚，最后一批输出也拖长流水尾部。

MoK 把每轮传输的 token 集合称为 minibatch，并开放调参。经验目标是让每个专家 grouped GEMM 至少拥有两个完整 wave。

SM 被明确分工

一部分 SM 执行专家 FFN，另一部分负责 dispatch 和 combine。两组通过本地计数器互相通知。

TMA load/store 只需不到三分之一的 SM 就能跑满 NVLink，因此通信与计算可以在不同 SM 上同时推进。

真正消除 CPU-GPU 同步的部件是环形 token 缓冲区。 MoK 用数百 MB 的固定 ring buffer 代替按实际 token 数动态分配的大缓冲区。dispatch 和 combine 跨 macrobatch 边界交错运行，槽位一被清空就立即复用。

确定性、精度与机架间通信没有被牺牲

MoK 固定浮点运算顺序。相同输入会得到逐位一致的输出。它支持 BF16 和 MXFP8，并在 MXFP8 模式下让共享专家继续使用 BF16，以保持训练稳定。

其任务通过 Blackwell 的 Cluster Launch Control 调度。高优先级流上的 FSDP all-gather 等机架间通信可以取得 SM，不必等整个巨型内核结束。

最值得带走的洞见

1. 分布式 MoE 的主要限制可能是通信和信令，而不是 GEMM 本身。
2. push 与 pull 应按操作选择。单一通信范式会错过调度和链路利用率优势。
3. 最佳重叠粒度位于两个极端之间，并应随模型形状和硬件调整。
4. 环形缓冲区能在不丢 token 的前提下移除动态分配所需的 CPU 同步。
5. 巨型内核已从少数手工专家才能驾驭的技术，变成可由小团队借助 AI agent 推进的系统工程。

今天，我们正式开源 Mixture-of-Kittens（MoK）。这是我们用于生产环境的 NVL72 MoE 训练巨型内核。

随着我们扩大 agent 编程模型 Composer 的训练和推理规模，混合专家层一直是主要瓶颈。根据负载和训练配置的不同，它可能占用端到端训练时间的一半以上。

MoK 把所有 MoE 通信和计算融合进一个完全确定性的内核，以解决这个瓶颈。目前，它已支撑 Composer 在数万块 GPU 上的训练。

你可以在 GitHub 上试用 MoK 并研究代码。我们期待收到反馈和社区贡献。

MoK 源于我们此前多次加速 MoE 层的尝试。过去一年里，我们编写了自己的 MXFP8 和 NVFP4 训练内核，还为 MoE 推理开发了“warp decode”方法。

不过，这些技术只优化了该层的计算部分，并假设 GPU 间通信会由其他组件处理。在生产负载中，通信已经成为限制因素。因此，我们从基本原理出发，重新设计了整个 MoE 层，并把通信直接放进内核。

此外，转向 GB300 NVL72 后，问题在两个方面发生了变化。第一，一个 NVL72 是位于同一 NVLink 域内的多节点机架。这让全部 72 块 GPU 可以快速、细粒度地重叠计算与通信。

第二，集成式 Grace CPU，也就是 GB300 名称中的“G”，与 GPU 相比往往较慢。我们发现 GPU stream 很容易追上 CPU 侧任务。此时 GPU 会完全空闲。因此，我们必须尽可能减少 CPU 工作和 CPU-GPU 同步。

我们针对这些挑战提出了 Mixture-of-Kittens（MoK）。这是一个从基本原理出发、专为 NVL72 高度优化的 MoE 训练巨型内核。MoK 把所有 MoE 通信和计算融合进单个内核。它完全确定，并且相对于公开实现达到了当前最佳性能。

在 MoE 中重叠计算与通信

MoK 面向 DeepSeek-V3（DSV3）风格的 MoE 层。这种结构广泛用于 GLM、Qwen、Kimi（截至 K2.7）和 DSV 等开放权重模型。此类 MoE 层把一个共享专家与大量路由专家组合起来。路由专家通常多达数百个。

每个 token 进入 MoE 层后，路由投影会选出 top-k 路由专家，并为每个专家分配一个路由权重。每个被选中的专家随后执行标准前馈网络计算，包括 up 投影、gate 投影、SwiGLU 激活和 down 投影。该层最后使用路由权重，合并共享专家和路由专家的输出。

本文使用以下记号：

  • D：模型维度
  • I：专家中间维度
  • E：路由选中的 top-k 专家集合
  • 输入 token：x ∈ RD
  • 路由权重：s ∈ R|E|
  • 专家权重：Wup ∈ RI×D、Wgate ∈ RI×D、Wdown ∈ RD×I

MoE 层随后执行相应计算，其中各项定义如上。原文此处的公式未包含在所提供的正文文本中。

在专家并行（EP）中，我们把路由专家分片，将其权重分布在多块 GPU，也就是多个 rank 上。共同持有全部专家权重的 rank 数量称为 EP degree。例如，有 256 个路由专家且 EP degree 为 64 时，每个 rank 持有 4 个路由专家，外加共享专家。因此，在进入和离开 MoE 层时，token 必须按照路由投影结果在 GPU 之间传输。

分布式 MoE 最直接的实现方式如下：先把每个 token 发送给持有其目标专家的 rank，这一步是 dispatch all-to-all；然后执行 FFN；接着把结果送回 token 原来的 rank，这一步是 combine all-to-all；最后对专家输出做加权求和。但通信耗时可能与计算本身相当。顺序执行两者效率很低。

标准解决办法是使用流水线，让 dispatch/combine1 通信与各专家的 FFN 重叠。系统先传输一批 token，然后在计算这批 token 的 FFN 时传输下一批，如此重复。MoK 是这种方案的一种实现。它加入了一组针对目标硬件的新技术，因此比现有基线更快。

选择正确的通信方向

在 GPU 间发送 token 时，可以选择基于 push 的机制。此时，持有 token 的 GPU 主动把数据写入远程目标 GPU。也可以选择基于 pull 的机制。此时，需要 token 的 GPU 从远程源 GPU 读取数据。现有方法在 GPU 间分散和收集 token 时，通常依赖 push 通信，例如 DeepEP。

一种常见看法是，push 所需的协议通信较少，因此更容易跑满 GPU 间链路，通常也就成为默认选择。不过，我们观察到两种机制各有取舍。要让性能最大化，必须为每个通信操作选择正确的方向。原因有三个。

调度

为了尽快完成 token 的 dispatch 和 combine，需要满足以下条件：

  • 连接机架内 72 块 GPU 的所有 NVLink 通道都必须保持饱和。不能长时间只让 token 经过部分“源端 → 目标端”通道。因此，在任意时刻，每个源 rank 发送的 token 都要均匀分布到所有目标 rank。
  • 发送给某个 rank 的 token 应按该 rank 的本地专家排列。如果到达顺序杂乱，按专家分组的 GEMM 就要等待更久，直到凑齐一个完整 token tile，Tensor Core 才能开始矩阵乘法。
  • 本地复制次数应为零。属于同一专家的 token 应直接落入连续内存。这样 grouped GEMM 无需本地重排即可开始。
  • 满足以上三个条件的额外开销必须尽可能小。绝大多数时间应花在实际发送 token 上，而不是调度或搜索待发送 token。

使用 push dispatch 时，需要生成一张包含 {src_index, dst_rank, dst_index} 三列的调度表。src_index 是本地输入激活缓冲区的索引。dst_index 是 token 在目标 rank 内存中的落点。表格的行序决定 token 通过 NVLink 发送的顺序。我们希望各行以 round-robin 方式轮换 dst_rank，让每条已连接通道都保持忙碌。

在目标为同一 dst_rank 的行中，dst_index 必须在所有源 GPU 之间均匀交错。它们还必须遵循目标 rank 上本地专家递增的顺序。构建这张表需要多次排序。每个 rank 的调度还必须考虑其他所有 rank，因为两个源 rank 不能写入同一个 dst_index。

Push 调度：连续条目必须交错选择目标 rank，才能让整个网络保持饱和。

Pull 调度：连续条目必须交错选择源 rank，才能让整个网络保持饱和。

使用 pull dispatch 时，调度表可以简化为两列：{src_rank, src_index}。表格的行索引直接对应本地目标缓冲区中的 token 索引。

理论上，调度表的行数应与目标缓冲区的行数一致。这会要求分配大量内存，后文会继续讨论。这里不需要排序。我们遍历路由投影结果。每当发现一个 token 应落到当前 rank，就把它的源 rank 和索引写入调度表。算法按此方式运行。

实际测试中，实现该算法的调度内核只占 MoE 总运行时间的不到 3%。它完全运行在设备端，不需要任何 CPU-GPU 通信。

如果为 combine 选择 push 方式，还可以原样复用这张调度表。只需把 {src_rank, src_index} 当作 {dst_rank, dst_index} 读取即可。事实上，我们只需构建一次调度表，就能在前向和反向过程中复用到全部四个通信操作：

  • 拉取式前向 dispatch
  • 推送式前向 combine
  • 拉取式反向 reverse-combine
  • 推送式反向 reverse-dispatch

最坏情况下，这张调度表也只有几 MB。长期保留不会形成内存压力。另一个好处是，它可以彻底消除 GPU 间的多通道信令。下文会进一步解释。

NVLink 带宽利用率

与所有网络系统一样，通过 NVLink 传输用户数据时，除了有效负载，还会附带协议元数据。元数据包含来源、目标和确认信息等内容，具体取决于网络协议。NVLink 通信协议的细节并未公开，但我们可以观察链路上传输的数据，并据此谨慎分析。

我们发现，push NVLink 通信传输的总字节数更少。这里的总量包括协议元数据和有效负载。它还会把几乎所有内容都沿同一方向发送。因此，当所有通道都处于繁忙状态时，它能取得更高的带宽利用率。

pull 传输的总字节数更多，但协议元数据会更均匀地分布到链路的两个方向。拉取方先向一个方向发送元数据，再从另一个方向接收更多元数据和有效负载。

我们可以编写一个简单的跨 GPU 传输内核，再用 NCU 分析它，以验证这一点。例如，在微基准中通过 NVLink 发送一个 256×256 BF16 tile，也就是 131,072B 时，我们得到了相应观察结果。

原文表格中的 RX 表示接收方向，TX 表示发送方向。可以看到，push 的总传输量大约少 12.4 KB。理想情况下，它应能带来更好的 NVLink 整体饱和度。不过，NVLink 在两个方向上使用独立通道。要达到 NVLink 规格标称的带宽，也就是 GB300 上第五代 NVLink 的 1.8 TB/s，流量必须在两个方向上充分流动。对于 MoE dispatch/combine 这类负载，每次传输通常只有几 KB，而且流量并不均衡，因此链路执行中会出现空泡。

实际结果显示，在专家负载不均时执行 token dispatch，pull 通信的 NVLink 带宽利用率最高比 push 高 29%。因此，pull 是更好的选择。

信令

GPU 必须知道 dispatch/combine 通信何时完成，所以信令不可缺少。GPU 只有收到完成信号后，才能开始处理接收到的 token。降低信令开销十分重要，而通信方向会对其产生明显影响。

使用 push dispatch 或 pull combine 时，完成信号必须跨 GPU 传播。在按专家分组的 GEMM 开始前，一个 rank 最多需要等待 71 个对等方发来信号。它还要发出 memory fence，在整个机架范围刷新内存。另外，信号仍在传输时，数据其实已经位于目标端，只是暂时不能使用。

使用 pull dispatch 和 push combine 时，跨 GPU 信令会消失。每个 rank 发起一次 load，等待数据到达，随后便能立即使用。不需要多节点同步。此外，只有单个实体负责信令，所以开销不会随专家并行规模增长。

我们发现，这部分信令开销相当大。在多节点微基准中，push dispatch 的信令延迟约为 pull dispatch 的 5.8 倍，分别为 103 微秒和 18 微秒。在巨型内核中，这些成本会快速累积。

基于上述结果，MoK 使用拉取式前向 dispatch、推送式前向 combine、拉取式反向 reverse-combine，以及推送式反向 reverse-dispatch。

合理组织计算与通信的重叠

计算与通信的粒度

计算与通信的粒度，是两类任务互相发送完成信号时所采用的工作粒度。这里存在一个值得注意的取舍。

在一个极端，通信可以非常细。例如，只发送刚好足以让 Tensor Core 启动一条完整矩阵乘加指令的 token。在 Blackwell 上，这个数量可以是 256。随后，让每次传输持续与矩阵乘法重叠。Comet 是这种方法的典型例子。

在另一个极端，通信可以很粗。系统一次发送数千或数万个 token，并等待整批数据全部到达，之后才启动 Tensor Core 操作。DeepEP 是这类方法的典型例子。

我们的观察是，这两个极端都不是正确选择。最优点位于两者之间，并且取决于实际负载。

如果通信粒度过细，Tensor Core 永远无法完全饱和。Nvidia Tensor Core 是高度流水化、面向带宽优化的加速器。我们应该持续向它们供给工作，而不是每隔几条 MMA 指令就遇到一次 barrier wait。

如果通信粒度过粗，Tensor Core 会长时间等待第一轮 token 到达，也会等待最后一轮输出完成 combine。

我们把每一轮发送的 token 集合称为一个 minibatch。MoK 把 minibatch 大小设为可调参数，因此在运行负载前可以方便地扫描候选配置。

选择最佳 minibatch 大小时，可以采用一个粗略的启发式方法：考虑每个算子需要多少个 wave，例如按专家分组的 GEMM。

一个 wave 是 GPU 上所有 SM 同时执行一轮任务。如果工作量太小，例如专家 grouped GEMM 收到的 token 过少，就会出现不完整 wave。此时部分 SM 会闲置。也可能出现尾部效应，也就是最后一个 wave 只使用部分 SM。

我们发现，让 FFN 中的每个专家 grouped GEMM 至少拥有两个完整 wave，是一种有效的 minibatch 大小选择方式。原因有两个。第一，一个完整 wave 已足以完全跑满 Tensor Core。第二，有两个 wave 时，第二个 wave 的 MMA 可以与第一个 wave 的 epilogue 及其依赖算子重叠，例如 SwiGLU 激活或下一个 grouped GEMM，从而摊薄尾部效应。

具体来说，在 Blackwell GPU 上，要充分利用 Tensor Core 执行 M×N×K GEMM，其中 K 是归约维度，每个 SM 都需要处理一个 128×256 的输出 tile。无论使用 1-SM 还是 2-SM MMA，都是如此。

设：

  • T：每次传输的 token 数，也就是 minibatch 大小
  • H：隐藏维度
  • I：专家中间维度
  • C：SM 数量

我们希望每个 GEMM 产生足以填满至少两个 wave 的任务，同时把通信粒度保持在尽可能小的水平，以获得最大重叠。对于 up 和 gate 投影，两者不存在依赖，可以同时运行，因此需要满足相应条件。

对于不能与其他算子并行执行的 down 投影，则需要满足另一项相应条件。

综合两者，便可得到所需约束。原文提供的正文文本没有包含这些公式的具体表达式。

以 Kimi 2.5 为例。它是 Composer 2.5 的基础模型，其参数为 H=7168、I=2048。Blackwell GPU 的 C=148。代入这些值后可以得到相应结果。原文提供的正文文本没有包含该计算式。

在针对 Kimi 2.5 形状运行 MoK 前向的微基准中，我们观察到了与这一启发式方法大致一致的结果。

安排重叠任务

确定通信粒度后，下一个问题是如何在 GPU 上安排 dispatch、combine 和 FFN，让它们高效重叠。为此，我们采用 inter-SM overlapping 技术。一部分 SM 分配给专家 FFN，称为 comp SM；另一部分分配给 dispatch/combine，称为 comms SM。两组 SM 通过一个本地计数器互相发送信号。由于 TMA load/store 只需不到三分之一的 SM 就能完全跑满 NVLink 带宽，这种分工是可行的。

我们把 inter-SM overlapping 作为基础策略。在 MoE 前向过程中，comms SM 首先执行拉取式 dispatch all-to-all。每当一个完整 minibatch 的 token 到达并可以计算时，它们就通知 comp SM。comp SM 随后对这些 token 原子式地执行 MLP-SwiGLU。所有操作完成 down 投影后，comp SM 再通知 comms SM，表示 token 已可进行 combine。

comms SM 会先处理全部 dispatch 任务，再处理 combine all-to-all。因此，当 dispatch 完成时，comp SM 通常已经发来了许多完成信号。随后，comms SM 开始执行推送式 combine，同时 comp SM 继续完成最后到达的 token 所对应的 FFN。此外，在 comp SM 等待第一次 dispatch 完成时，还可以插入共享专家 FFN。

反向过程与此类似，但加入前向重放后会稍微复杂。后文会详细介绍。comms SM 执行 reverse-combine，并通知 comp SM 运行不含权重梯度的 FFN backward，也就是三个 dgrad 专家 grouped GEMM 和 SwiGLU 激活反向。FFN 完成后，comp SM 通知 comms SM，说明 token 已可进行 reverse-dispatch。

全部 minibatch 的 dgrad 完成后，我们再计算剩余的三个 wgrad。推迟 wgrad 有两个原因。第一，reverse-dispatch 不依赖 wgrad，因此 wgrad 可以与最后几次 reverse-dispatch 重叠。第二，对 wgrad 而言，token 轴是归约维度。一次性沿完整 token 轴进行累加，可以尽量降低数值不稳定性。与前向过程相同，我们让完整的共享专家反向与第一轮 reverse-combine 重叠。

用环形 token 缓冲区彻底消除 CPU-GPU 同步

最后一个缺失环节是处理 MoE 的动态性。我们无法提前知道会有多少 token 到达某个目标 rank。

现有方案有两种。第一种是丢弃 token。超出固定缓冲区容量的 token 会被直接忽略，永远不会进入专家 FFN。第二种是 CPU-GPU 同步。系统把根据路由结果算出的各 rank token 数发送到 CPU，再由 CPU 分配大小刚好匹配的缓冲区。

两种方案都有明显缺点。我们不愿为了训练质量而丢弃 token。CPU-GPU 同步也会阻止 GPU stream 跑在 CPU thread 前面。

CPU-GPU 同步在 GB300 NVL72 上尤其昂贵，因为集成式 Grace CPU 很慢。在我们的 trace 中，GPU kernel 经常受到 CPU 任务限制，例如日志记录或把训练指标推送到远程服务器。同一套训练栈在使用 Intel CPU 的 DGX 机器上并没有这些问题。因此，我们希望尽量减少 CPU-GPU 同步。

MoK 使用一种环形 token 缓冲区来解决问题。我们将其称为 macrobatch。我们不再分配一个很大但大部分空间闲置的目标缓冲区，而是创建一个只有数百 MB 的固定环形缓冲区，并以 minibatch 为粒度循环使用。

高效实现 macrobatching，需要谨慎重叠计算与通信。两者都不应因为某个缓冲区槽位仍在使用，或槽位数据尚未到达而停顿。理想情况下，重叠应跨越环形边界。系统一边计算缓冲区尾部的数据，一边向缓冲区开头执行 dispatch。

关键思路是在性能允许时尽早排空每个槽位，使其尽快被复用。在前向过程中，dispatch 填充槽位，combine 排空槽位，再将其释放给下一次 dispatch。

不过，如果像上一节的调度一样，先完成所有 dispatch，再完成所有 combine，下一个 macrobatch 就必须等到全部 combine 结束才能启动。计算与通信也要等到下一 macrobatch 的第一次 dispatch 完成后，才能重新开始重叠。

为避免这个问题，我们在前向过程中交错执行 dispatch 和 combine。系统把前一个 macrobatch 某个 minibatch 的 combine，与下一个 macrobatch 对应 minibatch 的 dispatch 交错起来。两者使用环形缓冲区的同一区域。这样，缓冲区一被清空就会立即重新填充。第一个 macrobatch 的 dispatch 和最后一个 macrobatch 的 combine 没有对应任务，因此不会交错。

使用反向环，减少反向过程中的前向重放

反向过程稍微复杂，因为反向巨型内核必须支持前向激活重放。macrobatch 缓冲区是环形结构。如果存在多个 macrobatch，前向过程中保存的部分激活会被覆盖，因此必须重新计算。重放只需运行到 SwiGLU 激活为止，因为反向过程只需要 down 投影的输入激活和输出梯度，不需要它的前向输出。

这里的一项关键优化是反向环。如果按 macrobatch 升序处理 token，最后一个 macrobatch 会让环形缓冲区只填充一部分，反向过程最终需要重放更多激活。因此，MoK 在前向过程中按 macrobatch 的逆序遍历 token。这样，保存下来的环形缓冲区要么完全填满，要么包含全部 token，从而最大限度减少反向过程中的前向重放。

其他功能与实现细节

巨型内核

我们使用 megakernel 技术构建 MoK。指令在 SM 任务层面重叠，而不是被内核启动边界分隔。巨型内核通常适合融合完整的前向或反向步骤。我们发现它对 MoK 也很有用，原因有两个。

第一，如果不使用巨型内核融合，实现 minibatching 和 macrobatching 会需要多次启动内核，从而增加启动边界的开销。第二，在 inter-SM overlapping 中，我们发现使用多个 stream 和 green context 无法可靠地按预期精确划分 SM。软件划分则能提供精确的分配保证。

确定性

为了支持内部消融实验和 on-policy RL 后训练，我们把 MoK 设计为完全确定。浮点运算的顺序是固定的。因此，无论硬件怎样调度和发射指令，相同输入都会产生逐位一致的输出。

使用 Cluster Launch Control 重叠 RDMA

MoK 巨型内核通过 Cluster Launch Control（CLC）调度任务，以支持 RDMA 重叠。CLC 是 Blackwell 引入的一项硬件原生 work-stealing 功能，也是实现 persistent grid kernel 的一种新方式。

基于 CLC 的内核可以自然地把执行资源让给更高优先级 stream 上的内核，不必等待当前内核完全结束。这一点很重要。训练期间，我们经常需要让机架内通信和计算与机架间 InfiniBand/RoCE 通信重叠，例如 FSDP all-gather。这些通信本身也需要使用 SM。如果没有 CLC，机架间通信就会排在巨型内核之后串行执行，造成明显的性能下降。

MXFP8 支持

MoK 同时支持 BF16 和 MXFP8 精度模式。我们使用 MXFP8 模式训练，因为它速度更快，也没有引发数值问题。在 MXFP8 模式下，共享专家仍使用 BF16。我们发现，这样做会影响训练稳定性。

MXFP8 的一项额外成本是，张量送入 Tensor Core 前必须量化。为降低这部分开销，我们做了两项工作。第一，提供优化后的 MXFP8 量化内核，用于预先量化权重。第二，把激活量化融合进 dispatch all-to-all、专家 grouped GEMM 和 SwiGLU。

路由权重梯度计算

MoK 的反向过程还会使用类似 SonicMoE 的计算方式，求出路由权重梯度。它不会保存完整的 down 投影输出，而是通过 SwiGLU 激活与 down 投影 dgrad 的内积进行计算。这项计算被融合进 SwiGLU backward，以避免额外的内存流量。

计算与通信 SM 调优

comp SM 和 comms SM 的最佳比例取决于工作负载。本地 token 数、模型形状、硬件算力和网络带宽，都会改变 dispatch/combine 相对于专家 FFN 的耗时。即使负载相同，前向和反向过程的最佳比例也不一样。因此，MoK 提供了可调参数，可以分别设置前向和反向使用的 comms SM 数量。

加速效果

我们用两类 benchmark 评估 MoK。第一类是单个 MoE 层的 benchmark，我们公开了全部测试代码。第二类是在内部生产训练栈上跨多个 NVL72 机架执行的端到端 benchmark。

面向 agent 时代的巨型内核

Mixture-of-Kittens 从今天起完全开源。我们计划持续维护它，也欢迎社区提供反馈和贡献。我们希望它能降低 AI 研究门槛，让更多研究者和实验室高效训练模型。

MoK 也以灵活性为目标。我们投入了大量精力，让它易于修改。借助 agent，你可以迅速把它适配到我们当前使用范围之外的平台。

顺带一提，随着 AI 模型具备编写高性能内核的能力，内核优化领域变得有趣得多。过去需要手工编写的单算子内核，如今几乎可以完全交给 AI。只要给出正确的设计方向，例如如何让 warp 专门化，以及使用哪些 PTX 指令，agent 就能一次生成达到当前最佳水平的内核。

更有意思的是，它为我们带来了新的能力。去年，编写巨型内核需要先创建一层简化抽象。今年，我们不再需要框架。我们移除了额外的抽象层，并借助 agent，从零开始直接处理复杂问题。

agent 自动完成了较简单的任务，例如单算子内核。它们也帮助我们更快解决困难任务，例如编写分布式 MoE 巨型内核。整个项目只需要一支很小的团队。
