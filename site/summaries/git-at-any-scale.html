任何规模下的 Git

Git at any scale

一句话总括：Cursor 用 S3 预写日志保存权威历史，并把普通 Git 仓库降为可随时重建的本地热缓存，由此摆脱了 Spokes 的固定副本数和三阶段提交瓶颈。

真正的问题不是存储，而是 Git 的访问方式

packfile 天生不适合远程随机读取

Git 对象形成有向无环图。每一步读取都要先取得上一步的指针。

对象在 packfile 中又可能分散存放，并以 delta 形式依赖其他对象。把对象或文件系统直接分布化，会把一次本地随机访问变成大量网络往返。

因此，问题不能仅靠分布式键值存储、NFS 或块级复制解决。

Cursor 保留了普通 Git 仓库

Continuity 仍在本地 NVMe 上运行标准 Git 仓库。它不修改 Git 协议，也不维护特制的 Git 分支。

改变的是事实来源。本地仓库只是热缓存，真正不可丢失的历史位于 S3 中的预写日志。

这让系统既能复用 Git 的成熟优化，又能重新设计复制和恢复机制。

100压力测试中的副本数量上限，读取吞吐量仍保持线性增长。
120 次/秒S3 Standard 上可持续处理的推送吞吐量，同时执行压缩和复制。
300+ 次/秒S3 Express One Zone 上的推送吞吐量，此时瓶颈转向 Git 本地压缩。
<10 msS3 元数据条件 GET 的平均耗时，用于确认副本是否最新。

一次推送如何成为全局一致的事实

1

同时落盘与上传

推送的 packfile 写入本地磁盘，同时作为独立 WAL 对象上传到 S3。

2

准备引用事务

本地 Git 仓库锁定并验证引用，但此时提交仍不可见。

3

原子更新索引

系统通过 S3 的 CAS 操作，把 WAL 条目写入索引并线性化所有推送。

4

副本按需追赶

副本收到 UDP 提示后从 S3 更新。即使提示丢失，读取前的条件 GET 仍能保证一致性。

Spokes 的优势与上限

它做对了什么

Spokes 在本地 NVMe 上保存普通 Git 仓库，并在 packfile 层复制数据。所有副本保持同步，所以 clone 和 fetch 可以落到任意副本。

这套架构从约 2013 年起运行良好，也成为许多 Git 托管服务的行业范式。

为什么现在不够用了

三阶段提交的每一步都受最慢节点限制。副本越多，推送吞吐量越差。

大型 monorepo 需要远多于三个副本。智能体创建的海量小仓库却仍要固定保留三个副本。

它的资源下限太高，扩展上限又太低。

Continuity 的关键转变不是把更多仓库复制到更多机器，而是让机器上的仓库不再承担权威状态。系统健康时追求速度，发生部署、故障转移或网络抖动时则优先保持正确。

最值得带走的洞见

强一致性仍是硬约束

Git 客户端、CI 和智能体都无法可靠地适应最终一致性。刚推送的提交必须立即可见。

对象存储可以成为事务历史

S3 不只保存 packfile。配合 WAL 索引和 CAS，它还能记录推送顺序、压缩事件和完整来源信息。

复制数量应随负载变化

大型 monorepo 可以拥有数百个副本。闲置小仓库可以没有常驻副本，并在访问时重建。

压缩决定了系统的长期吞吐量

副本越多，独立 repack 的 CPU 成本越高。Continuity 只让主节点压缩一次，再让其他副本下载结果，以带宽换取 CPU 和可用性。

大规模托管 Git 仓库是一场噩梦。

Linus Torvalds 设计第一版“来自地狱的信息管理器”时，心里只有一个非常具体的使用场景：他自己的需求。顺带一提，这真的是 Git 的宣传语，你可以查一下。

他想替换当时用于开发 Linux Kernel 的分布式版本控制系统 BitKeeper。新的系统当然也必须是分布式的。

Kernel 是一个不同寻常的软件项目。它高度去中心化，众多子系统分别由不同维护者负责。分布式版本控制系统很适合这种工作方式。

二十年后，Git 已经成为行业标准。但现实是，它的分布式特性带来的阻碍多于优势。

普通开源软件项目并不会采用去中心化的工作流程。普通公司更不会。它们会利用分布式模型的许多优点，例如离线工作和延迟推送，但仍然高度依赖一个中心化托管平台。

事实证明，托管 Git 仓库是一项极其困难的工作。

Git 难在哪里？

大规模托管 Git 仓库的挑战，来自 Git 本身的设计。

分布式版本控制系统意味着，一个仓库的所有实例都完全相同。Git 服务器上的仓库并没有任何特殊之处。适用于服务器仓库的规则，也同样适用于开发者笔记本上的仓库。

这乍看会让 Git 托管显得很简单。只要在磁盘上的仓库副本前放一个 HTTP 守护进程，就有了一台 Git 服务器。

然而，Git 存在许多棘手的扩展性和可靠性问题。实际情况恰恰相反。

在普通 Git 仓库中，代码和元数据，包括文件、提交与树，经过压缩后存储在 packfile 中。

packfile 是一种简单的二进制序列化格式。在本地计算机上处理它很方便，但在服务器端进行大规模管理并不理想。

packfile 是 Git 存储和网络传输的基本单元。从仓库推送或获取数据时，传输的也是 packfile。

Git 的设计本来就是这样。不过，你也可以合理地认为，它不一定非得如此。

毕竟，你无法控制用户使用的 Git 客户端。除非你愿意惹恼用户，并给使用流程增加大量阻力。

但是在自己的服务器内部，你想怎么做都可以。没有任何东西强制你使用 packfile，Linus 也不会过来检查。

唯一的限制是，所有 Git 网络操作仍然必须接收和发送 packfile。

多年来，尝试大规模托管 Git 仓库的公司逐渐发现，以 packfile 为基础的设计严重限制了可用性和扩展性。

packfile 是大型二进制文件。Git 必须通过文件系统访问它们。

在磁盘仓库前部署 HTTP 服务器的简单方案，很快就会触及上限。

理想情况下，一个仓库应该分布在许多磁盘和机器上。这样可以并行执行大量 Git 操作，也能在某台服务器崩溃时继续提供服务。

但该怎么实现？

大致有三条路线，复杂度依次增加：分布文件系统、分布 packfile，或者分布 Git 本身。

没有 packfile 的 Git

Git 是一个内容寻址数据存储系统。

Git 仓库中的所有对象，包括 blob、树和提交，都以自身内容的 SHA-1 作为键。

这在直觉上非常适合映射到分布式键值存储。键是 SHA-1，值是对象本身。这似乎能够以一种干净的方式横向扩展仓库存储。

但实际上，这种方案行不通。

问题在于，Git 仓库的实际结构是一个有向无环图，也就是 DAG。

你可以通过 SHA 查找任意对象。但即便执行仓库中最简单的操作，也必须一步步遍历这个 DAG。

如果要列出仓库最近发生的变化，就必须处理提交。

处理一个提交时，你会得到指向其根树的指针。从根树中，可以得到每个文件和子树的指针。从原始提交中，还可以得到指向其父提交的指针，也就是历史中的前一个提交。

关键在于，遍历过程中的每一步，都必须先取得前一个对象，才能知道下一个指针的值。

如果每次读取都要与分布式存储进行一次往返，成本会迅速失控。

以前已经有许多人尝试在对象层分布 Git。这类方案往往无法在大规模环境中工作。

其中最有希望的实现，来自我以前的导师 Shawn Pearce。当时他在 Google 的版本控制系统团队工作。

他的方案是把对象存入分布式哈希表。

这只有借助 JGit 才能实现。JGit 是用 Java 编写的定制 Git 实现。

和任何正宗的 Java 库一样，JGit 提供了足够多的接口、工厂和接口工厂，能够抽象普通 Git 仓库的全部细节。它甚至可以用分布式哈希表替换磁盘上的 packfile。

这个系统确实能够工作。普通 Git 操作的结果也足够好。

但 Git 协议本身仍要求通过网络发送 packfile，无论服务器如何存储数据都一样。这一限制使 git clone 的性能差到无法接受，最终整个设计被放弃。

GitHub 与文件系统

Git 开始走出 Linux Kernel 圈子的几年后，一家充满冲劲的初创公司在旧金山诞生了。

GitHub 成立于 2008 年，定位是一家社交编程平台。它当时极有先见之明的宣传语是：“托管 Git 仓库，不再让人痛苦得要命。”

我不是在开玩笑，你也可以查一下。

早在 2008 年，人们就已经形成广泛共识。尽管 Git 采用分布式设计，或许正因为如此，要让它对用户友好，仍然需要一种中心化的仓库托管方式。

而且，这件事做起来非常痛苦。GitHub 决心改变这种状况。

GitHub 最初是一个 Rails 单体应用。今天它在很大程度上仍然如此。

最早的版本运行在一台性能强劲的机器上。Ruby 服务器和仓库副本放在同一台机器的磁盘中。

扩展 Rails 应用很容易，只要部署更多实例即可。

但在这个场景中，因为涉及 Git，他们很快又遇到了本文一直试图解决的问题：如果 Rails 应用需要访问磁盘上的 Git 仓库，该如何部署更多应用副本？

GitHub 早期的系统工程师是一群精打细算的怪才。他们尝试了最简单、看起来最可能解决扩展问题的办法。

他们认为，如果专注于分布文件系统，而不是分布 packfile 或 Git 本身，就可以保持 Rails 应用不变。

这样一来，他们就能把时间用于为不断增长的用户群开发更多功能，而不是折腾 Git 的内部机制。这个想法很务实。

但它没有成功。

团队尝试了多种用于 Git 数据的分布式文件系统方案。

最明显的方案是使用 NFS，把所有仓库存储在一台中心服务器上。这个方案很快就被放弃了。

Git 的默认实现对文件系统语义做了许多假设，包括锁定、写入撕裂、读取和同步等。

这些假设可以让 Git 在开发者那台缓慢笔记本的本地文件系统上获得不错的性能，却完全没有考虑它们在网络文件系统上的表现。

结果既慢，又容易出错。

之后，团队又尝试了一些按块复制文件系统的技术。现在回头看，这些技术坦率地说相当可怕。

其中包括一次短暂的 GFS 部署，以及一次持续时间更长、基于 DRBD 的部署。

它们最终全都撞上了墙。日常运维非常糟糕，性能也没有好到足以弥补这些问题。

归根结底，问题还是磁盘上 packfile 的设计。

前面已经讲过，Git 的图结构会让网络往返成本高得难以接受。

遗憾的是，相似的原理也适用于底层磁盘数据。

DAG 中对象的布局，与它们在 packfile 中的存放方式没有关联。

生成 packfile 时，最主要的启发式目标是尽可能减小文件大小。

对象会随机分布在整个 packfile 中，并经过压缩。更关键的是，它们很少以完整形式存储。

大部分对象都以同一 packfile 中另一个对象的 delta 形式保存。

因此，在沿着图数据结构进行多次逻辑跳转后，读取一个对象还要继续沿着磁盘格式进行多次物理跳转。

每一次 Git 仓库操作，都要在数 GB 数据中执行这种随机遍历。

无论网络文件系统在文件层还是块层进行复制，这种访问方式都无法良好运行。

只有把整个文件缓存在本地，才不至于让性能慢到无法使用。

但当同一个文件系统中存在数十万个仓库时，全量缓存并不可行。

最终，GitHub 的系统工程师硬着头皮放弃了分布式文件系统。

他们开始开发 RPC 系统，让仓库驻留在专用文件服务器上。同时，他们修改 Rails 应用，让所有操作都通过远程调用完成。

这带来了相当程度的水平扩展能力，但没有解决可用性问题，也没有改善最繁忙仓库的性能。

毕竟，每个仓库仍然只存放在一台机器上。

Spokes 与一致性

Spokes 最初由 GitHub 在 2013 年前后开发，后来逐渐成为行业标准。

大多数 Git 托管服务的架构都采用了某种 Spokes 变体，也就是在应用层复制 Git 仓库。

Spokes 能够稳定运行许多年，主要是因为它做出了三个基础选择。时间已经证明，这些选择是正确的：

  • 它不分布 Git 本身，而是在 packfile 层工作。
  • 它把所有数据保存为位于本地 NVMe 磁盘上的真实 Git 仓库。
  • 它复制 Git 数据，并让所有副本始终保持一致同步。

由于前面讨论过的 packfile 随机读取模式，要保证所有基础 Git 操作保持快速，基本上必须把普通 Git 仓库存储在 NVMe 磁盘上。

这也能保持 clone 的效率，因为不需要把数据转换成 Git 客户端所期待的格式。

它还允许团队把精力放在 Git 之上的产品开发中，而不是自行维护一个能够操作特殊仓库的 Git 分支。

让所有数据副本持续保持一致也非常重要。

这是一个通常要吃过苦头才能领会的事实：Git 客户端无法很好地适应最终一致性。

如果本地 Git 客户端推送了一个提交，却在紧接着的 fetch 中读不到它，情况会很糟。Git 会对此感到非常困惑。

如果 CI 流水线在一百个 runner 上运行，而其中三个 runner 在 clone 仓库后找不到应该测试的提交，情况同样很糟。用户体验也会非常差。

无论是在客户端还是后端，使用最终一致的 Git 仓库视图都会遇到许多危险的边缘情况。

因此，Spokes 付出了非常高的复杂度成本，确保系统始终完全一致。

下面看看这具体意味着什么。

Spokes 是一个基于共识的分布式系统。

它会在不同服务器上保存同一个 Git 仓库的多个副本。

每当推送新数据时，协调器都会把推送扇出，让仓库的每个实例都收到一份副本。

这一扇出过程通过经典的 3PC，也就是三阶段提交算法进行同步。只有大多数节点确认后，推送才会被接受。

三阶段提交与 Git 本身没有关系。

它是一种共识算法，用三个往返阶段确保系统中的所有节点一致决定提交或回滚某个事务。

它与两阶段提交非常相似，但额外加入了一个“预提交”阶段。这样一来，如果协调器在事务进行到一半时离线，系统仍然可以恢复。

要继续讨论 Spokes 如何使用 3PC，首先需要理解 Git 推送的工作方式。

一次 Git 推送包含两个组成部分：一个 packfile 和一个引用事务。

前面已经讨论过 packfile。它包含被推送到仓库中的对象，包括带有改动的 blob、树和提交。

引用事务会更新一个或多个引用，例如当前工作的分支，让它们指向刚刚推送的提交。真正发布改动的是这个事务。

这种分离在这里非常方便。

在指向某个提交的引用完成更新之前，这个提交并不可见。按照 Git 的说法，它还“不可达”。

因此，可以把 packfile 同时扇出到所有主机，而不需要同步这一过程。

随后，只需对引用事务执行三阶段提交。引用事务远小于 packfile，同步速度也快得多。

Git 本身支持准备引用事务。它可以锁定引用，确认现有值是否符合预期，然后一直持有锁，直到收到事务的提交或中止命令。

Spokes 会先分发 pack，再对每次推送的事务执行三阶段提交。

你可以在模拟器中增加副本数量和延迟，观察它们如何影响提交吞吐量。

通过这种设计，每次推送都会在所有副本之间完全同步。

之后，读取操作，也就是 fetch 和 clone，就可以安全地路由到任何单个副本，因为每个副本始终都是最新的。

这基本就是 Spokes 的工作方式。过去 13 年里，它一直运行得相当不错。

当然，Spokes 并不完美。没有任何系统是完美的。

到了 2026 年，人们使用 Git 仓库的方式已经发生巨大变化。我们也在构建分布式系统的过程中学到了许多重要经验。

时间和经验已经证明，Spokes 的哪些选择确实最优，哪些选择并非如此。

其中一个后来变得至关重要的缺陷，是 3PC 对水平扩展的限制。

Spokes 最初发布时，每个仓库使用三个副本是最合适的配置。

三个副本足以为普通仓库提供充裕容量。即使一台机器宕机，剩余副本也能提供足够的冗余并继续接受推送。

2026 年的情况已经完全不同。

企业公司的普通仓库如今往往是一个庞大的 monorepo。三个副本不足以承载这类仓库的流量，CI 场景尤其如此。

当然，Spokes 并没有禁止使用三个以上的副本。真正的阻碍是令人畏惧的“规模化长尾”。

三阶段提交与 Git 事务模型结合得非常优雅。但作为共识算法，它存在基础限制。

每一步的延迟都取决于集群中最慢的服务器。

集群中的副本越多，推送吞吐量就越差。

这一扩展限制在另一个方向上同样存在。

智能体大规模操作 Git 仓库时，常常不会把所有工作放在 monorepo 中。它们会创建数量庞大的小仓库，其中许多是临时仓库，大多数几乎不会被访问。

Spokes 也难以处理这种场景，因为它仍然要求每个仓库都拥有三个副本。

这意味着要保留三个大部分时间都处于闲置状态的副本。

又不能削减副本数量，否则系统将无法保持完全一致，并可能发生数据丢失。

采用三阶段提交时，资源下限总是太高，扩展上限又总是太低。

Spokes 还有一个缺陷。这个问题无法事先预见，但经历过以后就会变得极其明显：大规模运维 Spokes 可能非常艰难。

磁盘上的仓库始终是共识过程的事实来源，因此每个仓库的每个副本都非常重要。

你必须把仓库当作宠物，而不是可以随时替换的牲畜。

首先，这意味着你必须准确知道每个仓库位于什么位置。

系统因此依赖一个外部数据库。这个数据库需要维护一张非常庞大的路由表，把每个仓库映射到承载其副本的每台机器。

这项依赖本身也可能造成可用性问题。

每个仓库还必须计算校验和，并不断在路由表中更新校验和，确保磁盘上的仓库仍然有效。

一旦仓库出现问题，就必须立刻检测出来，并安排修复任务使其恢复健康。相信我，问题会频繁发生，Git 在实际环境中可能非常难伺候。

而且修复必须非常快。

因为磁盘上的仓库就是事实来源。损坏的副本和缺失的副本一样糟糕。

如果三个副本中有两个损坏，系统就无法继续接受推送，因为它已经无法形成法定多数。

Continuity

Continuity，简称 Cnt，是我们在 Cursor 开发的 Git 存储系统。

它的思路非常明确：吸收 Spokes 做对的一切，并修复我们经过多年实践后已经确认的问题。

Cnt 是一个简单的系统。一个系统如果不简单，就不可能易于运维。

它背后的核心原语是预写日志，也就是 WAL。我们把 WAL 存储在兼容 S3 的对象存储中。

生产环境直接使用 S3，但系统设计允许它部署在任何云平台上。

仓库收到推送时，我们会把这次推送作为一条 WAL 记录存入 S3。

只有在推送被完全持久化后，系统才会返回确认。

每次推送都存储为一个独立对象。被推送的 packfile 会同时写入磁盘并上传到 S3。

不过，上传 WAL 条目并不等于发布它。

只有在本地仓库副本上成功准备引用事务，并在 WAL 索引文件中记录指向该 WAL 条目的指针后，推送才会变得可见。

WAL 索引文件本身也是对象存储中的一个独立对象。

这种方式迫使所有推送都具备线性一致性。

我们尽量避免为每次推送单独执行一次 S3 写入。

在繁忙仓库中，这会让推送吞吐量受到 S3 PUT 延迟的硬性限制。

通过精心调校的批处理实现，再加上只需与单个本地仓库同步引用事务，而不需要与法定数量的副本同步，系统可以按照磁盘所能承受的最快速度接收推送。

本地仓库副本当然仍然是普通 Git 仓库，并存储在速度非常快的 NVMe 磁盘上。

我们在这一点上沿用了 Spokes 的做法，因为我认为 Spokes 完全做对了。

这使我们能够复用 Git 社区所有优秀的开源成果，包括上游 Git 客户端及其众多性能优化。

我们可以专注于交付新功能，而不是折腾 Git 的内部机制。

共识

前面已经看到，Spokes 集群难以运维的一个原因，是系统必须持续追踪每台服务器上每个仓库的位置。

Cnt 的处理方式完全不同。

每个仓库究竟位于哪里？答案是：“任何地方。”

这不重要。

我们把磁盘上的仓库视为热缓存。事实来源始终是 S3 中的预写日志。

系统本身无状态，也没有路由表，因此不需要运维关系数据库。这真是谢天谢地。

如果访问某个仓库时，本地磁盘上没有它，我们就直接根据 WAL 将它实体化。

这个过程可以非常高效。

当然，我们不希望总是这样做，因为那会造成浪费。

在生产环境中，我们使用 rendezvous hashing，把仓库 ID 映射到预计保存该仓库的一组节点。

路由仓库所需的全部状态，只有仓库 ID 和集群当前的健康节点集合。

即使这些状态没有及时同步，例如某个节点变得不健康，也完全没有问题。

我们只需在排名中的下一个节点上实体化仓库。

那么，共识怎么办？选举怎么办？某个仓库的主服务器是哪一台？

这些同样不重要。

这里没有状态，也没有共识。任何服务器都可以成为主服务器。

预写日志的所有更新，都通过 S3 上的原子比较并交换操作，也就是 CAS，进行同步。

因此，让仓库的任意实例接收推送始终是安全的。

和路由一样，让任意服务器充当主服务器并不是最高效的方式。它会导致 CAS 重试，并可能延迟推送。

所以在实际环境中，我们总是选择同一台服务器作为主服务器，也就是 rendezvous hashing 排名列表中的第一台服务器。

但在部署、故障转移或短暂网络异常等边缘场景中，我们根本不在意究竟哪台服务器是主服务器。

系统的设计目标是：降级时始终正确，健康时始终快速。

复制

在 S3 中保存预写日志，为系统扩展打开了全新的可能性。

我们实际上可以拥有任意数量的副本。S3 的扩展能力无可匹敌，所有副本都可以直接从那里追赶最新状态。

我们通过在集群中发送 gossip UDP 数据包进行乐观复制。

这些数据包包含每个副本在一次推送后直接从 S3 追赶状态所需的全部元数据。

我仿佛听见屏幕另一端、跨越时间与空间的你小声嘀咕：“这太疯狂了，UDP 不是可靠的传输协议。”

它当然不可靠。

分布式系统中没有任何东西是可靠的。线路不可靠，路由不可靠，拓扑同样不可靠。

但这没关系，因为它并不重要。

每个副本都知道自己最后追赶到的 WAL 索引版本对应的 ETag。

在副本上执行读取操作时，我们会使用预期的 ETag 向 S3 发起条件 GET 请求。

如果返回不带响应正文的 304，就表示副本已经是最新状态，可以立即提供 fetch 或 clone。

这项操作非常快。因为它只是一次 S3 元数据操作，平均耗时不到 10 毫秒。

如果返回 200，响应中会包含最新版 WAL 索引。我们会先用它追赶最新状态，再提供读取服务。

复制用的 UDP 数据包是否丢失，并不重要。

如果集群拓扑发生变化，数据包抵达了错误的服务器，也不重要。

所有副本上的所有读取都完全一致，因为它们会对照事实来源 S3 进行验证。

系统的设计目标仍然是：降级时始终正确，健康时始终快速。

这会带来两方面影响。

第一，由于系统始终一致，在它之上构建基础设施非常简单。

我们、我们的智能体、网页界面和客户端，始终都能看到全局一致的仓库视图。

第二，由于系统可以向两个方向扩展，每个仓库都能获得恰到好处的副本数量。

大型 monorepo 可以部署到数百个副本上，承载 CI 任务产生的全部负载。

智能体创建的数百万个小仓库，则可以各自只使用一个副本。

为了保证可用性，我们并不需要更多副本，因为 S3 才是事实来源。

事实上，闲置仓库甚至不需要保留一个副本。

如果某个副本长时间没有收到流量，我们就会从节点磁盘中回收它。下次出现 fetch 请求时，再根据 WAL 将其实体化。

压缩

预写日志需要定期压缩。

不能让日志无限增长。完整恢复需要重放每一条记录，因此记录越多，恢复成本就越高。

巧合的是，普通 Git 仓库同样需要定期压缩，尽管 Git 并不以 WAL 为基础。

前面已经看到，Git 仓库的基本存储单元是 packfile。

每次向远程仓库副本推送，或者向本地副本 fetch，都会创建一个新的 packfile。

这种方式无法无限扩展。

每个 packfile 都带有自己的索引。Git 可以通过索引高效查找其中的对象，但这种查找只在单个 packfile 内高效。

如果要查找某个特定对象，而仓库中有 100 个 packfile，就需要逐一打开每个 packfile 的索引并查找，直到在其中一个文件中找到对象。

一项高效操作如果必须执行数百次甚至数千次，就不再高效。

现代 Git 已经很擅长缓解这个问题。它现在支持多 pack 索引和增量几何压缩。

但最终仍然必须硬着头皮，对磁盘上的 Git 仓库重新打包。

在 Spokes 之类的系统中，这历来是一个持续存在的可用性问题。

即使采用增量方式，重新打包仍然是 CPU 开销非常高的操作，而且必须在系统的所有副本上执行。

如果不小心在同一仓库的两个或更多 Spokes 节点上同时触发维护操作，仓库很容易发生故障转移。

在 Continuity 中，我们会摊销压缩成本。

只有主服务器执行压缩。压缩结果同时应用于磁盘仓库和 WAL。

所有副本都会跟随 WAL，因此也会跟随其中的压缩事件。

副本不执行重新打包。它们只需从 S3 下载已经压缩好的 pack，以带宽换取 CPU。

规模

复制和压缩是决定 Git 存储系统在负载下表现的两个关键因素。

正如前面所见，两者存在内在联系。

仓库每秒接收的推送越多，读取性能下降得就越明显。每次推送产生的 packfile 都必须经过压缩，Git 操作才能保持高效。

如果要复制这些推送，就必须复制压缩结果，或者让每个副本独立执行压缩。

Continuity 以 WAL 为先的设计提供了完全一致的水平扩展能力。

你可以部署任意数量的副本。只读 Git 操作的吞吐量会随副本数量线性增长。

由于集群中的所有副本都完全一致，我们能够扩展 Git 协议操作，包括 clone 和 fetch。

也可以扩展 Origin 在仓库之上执行的所有 RPC 操作，包括网页界面交互、REST API 和各种智能体接口。

我们已经使用最多 100 个副本进行了合成压力测试。

测试中，读取能力始终保持线性扩展，推送吞吐量没有出现任何退化。

集群的推送吞吐量取决于更新 S3 上 WAL 的延迟。

使用 S3 Standard 时，系统可以持续处理每秒 120 次推送，同时执行压缩，并把压缩后的数据复制到所有其他节点。

我们还在 S3 Express One Zone 上部署了高性能集群。它的 PUT 操作延迟低得多。

在这种配置下，系统每秒可以接收超过 300 次推送。此时，真正的瓶颈变成了 Git 压缩磁盘数据的速度。

我们正在研究创新的数据磁盘布局方式，以降低压缩带来的影响。

我们的目标是在不放松严格持久性和一致性保证的前提下，继续提高 Git 仓库接收代码的速度。

以 WAL 为事实来源

S3 是一项很出色的技术。

由 S3 API 开创的 blob 存储理念，已经被证明是构建大型数据存储系统的强大基础组件。

这当然也适用于 Git 仓库托管。

本文介绍的设计在许多方面都很新颖，但它并不是第一个把 packfile 存储为 blob 的系统。

Azure DevOps，也就是 Microsoft 自己推出、与 Microsoft 旗下 GitHub 竞争的产品，拥有一套非常成功的 Git 存储系统。

它把 packfile 存储在 blob 存储中，并把引用存储在关系数据库 MS SQL Server 中。

这种系统存在许多取舍。

关系数据库很适合扩展大型引用事务，但你也因此必须运维一个关系数据库。

我们坚信，Git 数据的一致性比其他任何考虑都重要。

正是这一点最终让我们决定设计一个基于 WAL、且不依赖外部数据库的系统。

生产环境中的 Git 仓库可能出现许多问题。

静态数据损坏、重新打包期间的缺陷、推送期间的竞态条件。它就是一大堆边缘情况的集合。

上游 Git 已经解决了其中大部分问题，但并非全部。

没有任何系统不存在缺陷。即使它是开源软件，并已获得广泛部署，也不例外。

我们的一致性模型可以追踪仓库发生的每一项基础操作。

只有当推送完全持久化到 WAL 后，我们才会返回确认。

我们会线性化所有推送。

我们访问的每个仓库视图始终完全一致。

由于每次推送都位于 WAL 中，我们可以查看仓库曾经经历的每一个状态。

我们拥有所有推送的完整来源数据，也拥有所有重新打包操作的完整来源数据。

我们可以让任意副本回退或快进。

不需要与任何外部数据库同步状态，无论该数据库只保存引用，还是保存全部对象数据。

当我们在 Git 中遇到缺陷时，不是“如果”，而是“必然会发生”，我们可以精确定位发生了什么，并撤销相关操作。

除了 Git 中已经存在的缺陷，我们引入的新缺陷很少。

原因是整个过程中，所有 Git 操作仍然使用现成工具，在磁盘上的普通 Git 仓库中执行。

Origin

我们非常清楚，托管他人的源代码有多么重要。

我想，每一个读完并理解本文的人，也同样清楚这一点。

如果开发者无法向 Git 仓库推送代码或从中拉取代码，整个公司都可能停摆。

CI 系统停机五分钟造成的生产力损失，很难换算成具体金额。但无论用什么方式衡量，这个数字都会非常庞大。

智能体从根本上改变了我们的软件工作方式，也在许多方面加剧了这一问题。

更多代码、更多 PR、更多 CI 运行。

版本控制位于所有这些工作的核心，同时可能也是最难在一夜之间更换的基础设施。

过去许多个月里，我们在 Cursor 内部一直面对这些困难。

我们投入了大量思考和精力，构建一个能够为自己解决这些问题的平台，并希望它也能为客户解决问题。

当前，我们专注于提供尽可能顺畅的迁移出口，让用户获得更高的可靠性、性能和扩展能力，并尽可能减少迁移过程中的痛苦。

Origin 不是一项实验。

它由一群真正理解这些挑战规模的人打造，凝聚了他们数十年来构建同类系统的经验。

我们拥有已经被证明有效的工程与运维理念，也坚定承诺随着版本控制领域的发展继续改进它。

我们希望你愿意信任我们和我们的平台。
