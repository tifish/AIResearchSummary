我们如何搭建云端智能体环境

How we set up our cloud agent environment

一句话总括：Cursor 把开发环境当作面向智能体的产品，通过统一接口、端到端验证和自动修复，让云端智能体从辅助工具变成了主要代码贡献者。

约 10% 去年 12 月，云端智能体编写的已合并 PR 占比
→
> 50% 如今由云端智能体编写的代码占比

真正的瓶颈是环境

Cursor 的开发者主要使用 Mac，本地工具链却要在 Linux 云端 VM 中运行。构建命令、参数和脚本也很零散。

仅靠技能文档无法消除这些复杂性。命令本身仍然容易出错，智能体还要照看长期运行的进程。

智能体表现不稳定，不一定代表模型能力不足。它也可能只是被不一致、难以理解的环境拖住了。

把环境做成智能体可用的产品

团队先让云端环境与本地开发保持一致，并把关键依赖放进统一的 Dockerfile。

随后，他们用 anydev 收拢服务启动和常用工具。监督进程会自动监控并重启长期构建任务。

最后，Cursor Cloud MCP 和 Cloud Doctor 负责发现配置故障、分析根因，并在高置信度时提交修复 PR。

环境开始自愈后，智能体才能稳定完成端到端测试。开发者也更愿意直接合并和部署它们的代码。

能力提升形成了一条闭环

1

匹配本地环境

让 Ubuntu VM 获得开发者日常使用的依赖、数据和安全访问能力。

2

简化操作接口

用 anydev 统一启动服务、调用工具，并管理长期运行的任务。

3

自主测试证明

智能体运行端到端流程，录制演示，并向用户证明改动正确。

4

诊断并持续修复

Cloud Doctor 从失败轨迹中发现系统性问题，再修正技能、命令或环境。

模型需要的并不只是更多操作说明，而是一条更短、更稳定、能够自行恢复的成功路径。

这改变了理解 AI 编码能力的方式。衡量模型时，不能把环境质量视为固定背景。环境本身会决定智能体能否运行代码、验证结果，并获得开发者信任。

最值得带走的洞见

开发环境也是产品 它的用户不再只有人类开发者。仓库结构、工具接口和错误信息都要让智能体能够自行理解和操作。
文档不能替代简单接口 技能可以说明正确命令，但无法修复命令本身的复杂性和隐藏陷阱。
验证能力带来信任 当智能体可以完成端到端测试并提交录屏证明时，工程师不必在本地再次检出分支。
自愈机制会放大采用规模 环境越可靠，团队越敢把重要任务交给智能体。Cursor 的数据从约十分之一增长到超过一半，正体现了这种反馈循环。

当我们决定给云端智能体配备计算机，让它们能够测试自己的改动时，第一步就是确保它们能在我们自己的代码库中做好测试。

在让 monorepo 适配云端智能体的过程中，我们意识到，开发环境本身就是一种产品，只不过它的用户是智能体。你需要让云端环境与本地开发保持一致，让仓库足够易懂，使智能体不依赖团队内部的口口相传也能运行和测试代码。随着代码库不断变化，你还要持续维护这个环境的健康状态。

这个环境的建设改变了我们的工作方式。去年 12 月，云端智能体编写的代码约占 Cursor monorepo 已合并 PR 的十分之一。如今，它们编写的代码已经超过一半。

让云端开发与本地开发保持一致

要让云端智能体在我们的仓库中顺利工作，第一步是确保仓库能在云端 VM 中正常运行。任何首次配置远程开发环境的工程师，都会熟悉这个阶段。

大多数 Cursor 开发者都在本地 Mac 设备上工作，但我们的云端 VM 运行 Linux。因此，我们需要改造各种开发工具和设置脚本，使其不再依赖特定操作系统，并能在 Ubuntu VM 上运行。我们还把关键开发依赖加入 Cursor 定义的 Dockerfile。这个 Dockerfile 会作为云端智能体的初始镜像。

我们还与安全团队合作，为云端智能体产品增加了多项安全功能。这样，用户就能放心地把必要的密钥注入智能体环境。这些功能包括限制网络出站访问、提供限定范围并经过代理的 Git 远程访问、扫描提交内容和提交信息中的密钥，以及在工具返回结果中遮盖密钥。即使智能体尝试读取密钥值，最后一项措施也能阻止它得逞。

为智能体提供更简单的接口

即使开发环境已经能在 Ubuntu VM 上运行，智能体仍然不擅长运行我们的代码。这并不意外。我们的开发体验比较混乱，开发者需要学习并记住大量构建命令、构建参数和工具脚本。

我们为系统中的许多部分编写了构建和运行技能，但效果有限。技能可以记录正确的命令，可这些命令本身仍然十分复杂，其中还藏着许多容易踩中的陷阱。

为了降低复杂度，我们开发了一个名为 anydev 的 CLI。智能体可以用它启动所有服务。我们也通过 anydev 调用常用工具脚本，并为它配置了多个 --help 菜单，用来解释各个子命令的用法。anydev 还带有一个监督进程。它会监控并重启长期运行的构建命令，让模型完全不必承担这项工作。

anydev 把开发体验简化到了足够清晰的程度，使智能体能够可靠地运行代码。技能仍会说明如何使用它，但更重要的变化是，智能体不再需要同时处理冷门的多步骤构建命令，不必躲避隐藏的陷阱，也不用持续照看长期运行的进程。

从这个阶段开始，每个都拥有独立计算机的云端智能体，相比本地智能体真正体现出了额外价值。借助计算机操作能力、recordScreen 工具和可用的开发环境，智能体现在可以对改动进行端到端测试，并向用户证明工作成果是正确的。

智能体修复错误报告后，还可以在 Slack 中分享由自己录制的演示。它们开启 PR 时也能附上这类演示。面对许多任务，工程师现在可以放心地合并和部署云端智能体编写的代码，全程无须在本地检出对应分支。

打造可自愈的环境

智能体周围的环境一直在变化。要让它保持可用，就必须持续更新环境的运行方式，以及智能体能够访问的资源。

为了在环境出现故障时诊断问题并恢复运行，我们开发了 Cursor Cloud MCP。我们选择 MCP，是因为它可以提供动态发现的工具。即使工具接口发生变化，我们也不必重新构建智能体循环。云端智能体可以借助它检查自己的环境，查找设置失败、出站访问策略、已变更密钥等问题。这样，它们就能在问题出现时进行诊断和修复，让不健康的环境更快恢复。

部署 Cursor Cloud MCP 后，我们又建立了一套名为 Cloud Doctor 的自动化机制。它会定期检查故障，记录哪些错误可能只是暂时性问题，哪些错误值得关注。它还会分析根本原因，并在有较高把握时开启 PR 来修复问题。

改善智能体的开发体验

即使环境处于健康状态，智能体有时仍会采用耗时或绕远的方式验证改动。它们可能选错技能，在 VM 中遇到本可避免的问题，或者采用不必要的漫长工作流程。

在这里，我们同样会使用 Cursor Cloud MCP。Cloud Doctor 智能体会检查运行轨迹，找出另一个智能体在哪一步出了问题，哪些技能或命令容易造成误导，以及哪些工作流程总是异常缓慢。Cloud Doctor 会根据这些发现修复技能、简化操作路径，或者修改环境，让下一个智能体能更轻松地完成工作。

这个循环会持续改善智能体自己的开发体验。当环境健康并具备自愈能力时，智能体的运行会更加可靠，开发者也会愿意把更重要的工作交给云端智能体。

正因如此，我们才能在内部扩大云端智能体的使用规模。如今，我们发布的大部分代码都由它们编写。

让你的开发环境为云端智能体做好准备

对我们而言，云端智能体能否高效工作，主要取决于环境。要判断你的代码库是否已经准备就绪，可以先回答三个问题：

  • 智能体能否访问开发者会使用的同一套工具和数据？
  • 智能体能否找到准确记录开发者实际工作方式的技能？
  • 智能体能否测试并验证核心工作流程？
