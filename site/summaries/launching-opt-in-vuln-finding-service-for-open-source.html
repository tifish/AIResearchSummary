推出面向开源软件的自愿加入式漏洞发现服务

Launching an opt-in vulnerability-finding service for open-source software

一句话总括AI 找漏洞的速度已经远远甩开人工验证。Anthropic 因此推出 OSS Scanner，让开源维护者可以主动选择直接接收未经人工审核的模型报告。早期抽检显示，这些报告的误报率极低。

为什么要绕过人工审核

漏洞利用代码如今几分钟就能写出来。攻击者也在用同样的能力找同样的弱点。

旧路径：先验证，再披露

报告质量有保障。但受人力限制，大量候选漏洞积压未发。

对缺少资源的项目，Anthropic 会继续走这条协调漏洞披露（CVD）流程。

新路径：模型直出的快速通道

报告一生成就发出，扫描更快、更频繁。

这条路并非凭空设计。许多维护者收到首批报告后，主动要求一次拿到全部，哪怕未经验证。

在攻防竞速中，维护者愿意用一点准确性去换时间。新服务只是把这种需求变成了正式选项。

每份报告交付什么

报告由最强模型（含 Claude Mythos）生成。在数十个项目的试运行中，交付了数百份报告。其中多个漏洞被串联成无需身份验证的远程代码执行利用链。

独立复现程序

工程师拿到后可以直接跑起来验证。

漏洞解释

说明成因。条件允许时，还用二分查找定位漏洞是在哪次改动中引入的。

候选补丁

如有可用的修复方案，会一并附上。

附带复现和补丁，把“读报告”变成了“验证并合并”，大幅降低维护者的处理成本。

完整译文

我们正式推出 OSS Scanner。这是一个面向开源生态、需项目自愿加入（opt-in）的漏洞扫描服务。它的设计借鉴了我们在 Project Glasswing 中用 Claude 发现漏洞的经验。加入的项目将免费获得由我们最强模型执行的、全面且定期的安全扫描。

语言模型发现漏洞的能力进步很快，我们已在这个博客上多次详细报道。以学术漏洞发现基准 CyberGym 为例：去年年初，LLM 只能找出不到 20% 的漏洞；到了今年，这一比例已超过 85%。因此，开源维护者从 LLM 那里收到的东西，已经从过去以低质量内容（slop）为主，变成了高质量的漏洞报告。

过去六个月，我们用最新模型扫描了全球一些最重要的软件项目。我们发现了超过 29,000 个候选漏洞，但只对其中约 6,000 个完成了人工审核和分级处理（triage）。6,000 个漏洞已经是不小的数量。但我们验证这些发现的能力仍受限于人力，这个瓶颈依然存在。

我们正在扩大漏洞披露的规模。与此同时，越来越多的维护者在收到我们的首批报告后，直接要求我们把所有未经验证的报告连同修复建议一并批量提交。截至目前，应维护者“把手上所有内容都发过来，哪怕尚未验证”的要求，我们已直接向他们发送了近 5,000 份报告。如今，漏洞利用代码（exploit）几分钟就能开发出来。攻击者也在争分夺秒地寻找并利用同样的弱点。能更快发现并修复漏洞的项目，就能更好地保护自己的软件。

对于经人工验证的漏洞报告，我们将继续通过现有的协调漏洞披露（coordinated vulnerability disclosure，CVD）流程手动披露。对于没有资源自行分级处理报告的项目，这一点尤其重要。不过，我们现在也提供一条可选的快速通道，供希望第一时间收到漏洞报告的项目使用。

我们的漏洞扫描器

Google 的 OSS-Fuzz 用模糊测试器（fuzzer）扫描开源软件中的漏洞，给开源生态带来了积极影响。受此启发，我们推出 OSS Scanner，用我们最强的语言模型在开源代码中寻找漏洞。Claude Security 是我们面向大众开放的代码扫描与修补产品，重点是帮助企业保护自身系统。OSS Scanner 则为开源项目免费提供安全审计。

这一自愿加入的漏洞扫描器，其输出将完全由模型生成，不经过人工审核或分级处理。这样可以扫描得更快、更频繁。但这也意味着，报告有可能出错或无效。这些报告将由我们最强的模型（包括 Claude Mythos）生成，为开源项目提供最大的防御优势。

过去几周，我们和数十个开源项目一起验证了这条流程。最初的披露包含数百份漏洞报告。其中有多个漏洞，我们能够把它们串联起来，形成影响这些项目的无需身份验证的远程代码执行（unauthenticated remote code execution）利用链。每份报告都包含：一个可独立运行的复现程序（reproducer）；对漏洞的解释（在可能的情况下，包括通过二分查找确定漏洞何时引入）；以及修复该漏洞的候选补丁（如有）。现在，我们正把这项服务开放给更多开源项目。

以下是我们在测试 OSS Scanner 早期版本和原始模型输出时收到的部分反馈：

“OSS Scanner 的发现中，揭示 PostgreSQL 缺陷的比例异常地高。有几份报告附带的修复几乎可以原样使用。快速通道还让我们得以在最新问题进入正式版（GA）发布之前就把它们解决掉。”

——Noah Misch，PostgreSQL

——Anton Arapov，OpenSSL Corporation

“我们发现这些报告的信号质量很高：在收到的 74 份报告中，只有两份无效，还有五份成为了 CVE。报告附带补丁，因此能直接融入我们现有的问题验证与修复流程。我们希望收到更多。”

——Todd Ouska，wolfSSL

“这些漏洞报告详尽清晰，对 HotCRP 复杂的权限模型理解到位，漏洞优先级排序也做得很好。”

——Eddie Kohler，HotCRP

为了验证 OSS Scanner 的早期版本，我们请负责审核 CVD 发现的专业渗透测试人员，检查了扫描器在 48 个项目中找出的 97 个严重（critical）和高危（high-severity）漏洞。其中 85 个（88%）达到了我们 CVD 流程的标准。其余 12 个中，有 11 个是真实存在的漏洞，但与已知问题或本次扫描的其他发现重复；只有一个是无效的，也就是“误报”（false positive）。此后，我们已把其中许多发现发送给维护者。维护者很少告诉我们某个高危或严重发现是无效的，这与我们此前在开源领域的工作结果一致。也有维护者告诉我们，严重程度评级可能偏高，或者扫描器误解了项目的威胁模型。我们无法保证扫描器完美无缺。但我们会根据维护者的反馈，并随着模型的进步，持续改进这个系统。

开始使用

符合条件项目的核心维护者，可以按照标准项目模板向这个 GitHub 仓库提交 PR 来报名，我们的扩展 FAQ 中提供了更多指导。项目资格标准与 OSS-Fuzz 所用的标准类似。简单来说，项目应对“基础设施和用户安全具有关键影响”。我们会逐个评估并做出决定。

无论 OSS Scanner 是否适合你，我们新推出的 Cyber Verification Program 都会向符合条件的安全专业人员开放先进的网络安全能力，并减少拦截分类器的限制。Claude for OSS 则免费提供 Claude Max 20x 订阅，帮助修复漏洞、改进开源项目。
