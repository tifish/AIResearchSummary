Advancing coding in low‑resource programming languages

两项评估分别检验构建能力与行为保真

MultiLangBench：从零做出可用功能

模型需要用指定语言构建兼容 SQLite 的数据库引擎。评估通过数据库文件统一输入与输出，再用 SQLite 参考实现核验结果。

任务覆盖代码组织、状态管理、错误处理和功能扩展。它检验的是持续开发中的工程能力。

COBOL 迁移：保持原程序的输出

模型需要把 COBOL 程序迁移到 C++、Java、Kotlin、Python 或 Rust。隐藏测试要求可观察输出逐字节一致，只有全部测试通过才算成功。

这一标准把业务行为是否保留，放在了迁移是否成功的核心位置。

两项结果应分开理解：构建评估报告测试通过率，迁移评估则以全部测试通过作为成功条件。

能运行，不代表财务结果一致

COBOL 的定点运算默认截去多余小数位，只有明确要求时才舍入。迁移后的程序如果改为舍入，可能不报错，却产生不同的财务结果。

因此，评估成绩体现了行为保持能力的进展。用于生产软件时，仍需专家审查，并依据系统的业务规则和依赖关系进行测试。

这类编程能力的实际意义，在于帮助团队理解、维护和改造关键服务背后的既有软件。

最值得带走的洞见

  1. 新建与迁移是不同能力。前者看能实现多少功能，后者看能否保留原有行为。
  2. 语言覆盖扩大了，差距仍存在。Astra 在 19 种语言上超过 83%，COBOL 仍相对困难。
  3. 成本与能力可以同时改善。Luna 的构建评估与 GPT‑6.1 Sol 的低推理强度迁移评估都展示了这一点。
  4. 高分不能取代业务验证。舍入规则等细节足以让正常运行的迁移代码产生不同结果。

提升面向企业软件的能力

我们最新的模型进展，增强了在 COBOL、Fortran 和 Visual Basic 等低资源编程语言中构建和迁移软件的能力。与 Python、JavaScript 等语言相比，这些语言可供模型学习的代码和文档更少。但它们支撑着世界各地的关键基础设施和基本服务。COBOL 支撑着超过 40% 的网上银行系统、80% 的线下信用卡交易和 95% 的 ATM 交易（在新窗口中打开）。Fortran 则用于天气预报（在新窗口中打开）和核反应堆安全分析（在新窗口中打开）。提升 AI 处理这些语言的能力，可以帮助团队维护和改造基本服务所依赖的软件。

这项工作的方向来自开发者和企业客户的反馈。他们告诉我们，编程模型在处理这些语言时往往表现不佳。维护和改造此类软件可能很困难。文档可能不完整，最初的开发者可能已经离职，重要的业务规则也可能只存在于代码中。无论团队是在修复错误，还是将软件迁移到另一种语言，都需要保留系统所依赖的行为。

为了衡量进展，我们开发了两项评估。MultiLangBench 测试模型能否使用 20 种不同的编程语言，从零构建兼容 SQLite 的数据库引擎。我们的 COBOL 迁移评估则测试模型能否将现有程序迁移到另一种语言，同时保持其行为不变。两项评估共同检验了两种互补的能力：构建新软件，以及保留现有软件的功能与行为。

我们的最新模型在两项评估中都有显著进步，以更低的成本实现了高得多的准确率。

在 MultiLangBench 上，GPT‑6 Astra 在 20 种编程语言中的平均测试通过率达到 87.4%，高于 GPT‑5.6 Sol 的 26.8%。每种受测语言的表现都有提升。GPT‑6 Luna 也优于 GPT‑5.6 Sol，测试通过率达到 40.3%，估算 API 成本则低约 78%。

在我们的 COBOL 迁移评估中，GPT‑6.1 Sol 采用低推理强度时，准确率达到 86.6%。相比之下，GPT‑5.6 Sol 仅为 5.4%，而 GPT‑6.1 Sol 的成本还低了 39%。采用较高推理强度时，准确率达到 97.9%，几乎达到这项评估的上限。

这些结果共同表明，我们的模型处理多种编程语言的能力正在显著增强，成本效益也在提高。

1. 从零构建 SQLite（MultiLangBench）

MultiLangBench 要求模型使用指定的编程语言，构建一个兼容 SQLite 的数据库引擎。模型必须组织代码库、管理状态、处理错误，并在保留现有功能的同时添加新功能。

为了比较不同语言的实现，我们使用数据库文件作为统一接口。待评估程序接收一个初始数据库和一条 SQL 查询，然后输出修改后的数据库。我们使用 SQLite 的参考实现，检查输出数据库的内容是否符合预期。这样，无论构建引擎使用哪种语言，我们都能应用同一组测试。

我们将 SQLite 现有测试套件中的测试改编为这种格式。这项评估衡量模型在较长的编程会话中能实现多少可用功能，并同时报告测试通过率和 API 成本。

采用最高推理强度时，GPT‑6 Astra 在 20 种语言中的平均测试通过率达到 87.4%，高于 GPT‑5.6 Sol 的 26.8%。每种受测语言的表现都有提升。其中，COBOL 从 10.9% 升至 72.1%，OCaml 从 25.6% 升至 85.8%，Fortran 从 21.4% 升至 83.5%，Visual Basic 从 27.5% 升至 89.4%。Astra 在 20 种语言中的 19 种上得分超过 83%。COBOL 仍然最难，得分为 72%。

GPT‑6 Luna 提供了成本更低的选择，并且在每种受测语言上也都优于 GPT‑5.6 Sol。采用最高推理强度时，其平均测试通过率达到 40.3%。其中，COBOL 从 10.9% 升至 17.1%，OCaml 从 25.6% 升至 34.1%，Fortran 从 21.4% 升至 31.4%，Visual Basic 从 27.5% 升至 41.6%。实现这些提升时，每个样本的估算平均 API 成本为 0.77 美元。GPT‑5.6 Sol 则为 3.48 美元，前者约低 78%。

我们正在 GitHub 上发布 MultiLangBench 的评估配置和测试套件（在新窗口中打开），以及各语言的结果。开发者可以检查评估测试了哪些内容，查看自己使用的语言上的表现，并找出与自身工作相关的重要能力缺口。

2. 迁移 COBOL 代码库

我们的第二项评估要求模型将 COBOL 程序迁移到 C++、Java、Kotlin、Python 或 Rust，同时保持每个程序的功能与行为不变。

成功迁移既需要理解程序的业务逻辑，也需要理解 COBOL 特有的语言行为。COBOL 程序通常处理金融交易和业务记录。其中，舍入规则、记录缺失时的处理方式等细节，都体现了业务要求。例如，除非明确要求舍入，否则 COBOL 的定点运算会截去多余的小数位。如果重写后的程序改为对这些数值进行舍入，即使运行时没有报错，也可能产生不同的财务结果。

为了测试这些行为是否得以保留，我们使用隐藏测试评估模型，要求可观察输出逐字节一致。只有全部测试通过，迁移才算成功。此类保持行为不变的能力，对维护和改造老旧系统的团队很有用。不过，将其用于生产软件时，仍需要专家审查，并依据系统的业务规则和依赖关系进行测试。

在这项评估中，GPT‑6.1 Sol 采用低推理强度时，准确率达到 86.6%。GPT‑5.6 Sol 在相同设置下的准确率为 5.4%，而 GPT‑6.1 Sol 的 API 成本仅为其 61%。采用较高推理强度时，准确率达到 97.9%，使这项评估接近饱和。这些评估结果表明，在为团队提供更准确、更经济的代码迁移能力方面，我们取得了进展。这些团队正在改造其业务所依赖的软件。

提升面向企业软件的能力

这些评估，加上开发者和企业客户的直接反馈，帮助我们了解模型在哪些方面正在进步，又在哪些方面仍有不足。

我们的目标是帮助模型将软件工程技能应用到更多语言中。这些技能包括理解不熟悉的代码仓库、规划修改、使用构建工具、运行测试，以及调试失败问题。

你可以通过 API 试用我们的最新模型，让它们处理团队所用语言中的编程任务。欢迎反馈哪些方面表现良好、模型在哪些方面仍有困难，以及我们接下来应重点关注哪些语言或工作流程。这些反馈会帮助我们改进模型的训练和评估方式，从而更好地支持你所依赖的软件。
